# FLOW:
LOAD BALANCERS BEHAVE AS REVERSE PROXY FOR AUTHENTICATION AND AUTHORIZATION. 
IT STARTS WITH INBOUND SERVICE. USING INBOUND SERVICE DIFFERENT SELLERS WOULD LIST THEIR PRODUCTS IN AMAZON. THIS INFO WOULD BE SENT TO KAFKA. INBOUND SERVICE BEHAVES AS PRODUCER WHEREAS SEARCH SERVICE(BECAUSE IN NEAR FUTURE USER MAYBE SEARCHING THIS PRODUCT) AND INVENTORY SERVICE(ACTING AS SOURCE OF TRUTH HAVING REAL TIME UPDATE OF ITEM) WILL SERVE AS CONSUMER.  


# INVENTORY SERVICE:
IT IS RESPONSIBLE STORING THE REAL TIME INFORMATION OF ITEMS IN STOCK. WE WILL BE HAVING PRODUCT CATALOG TABLE IN WHICH WE WILL BE STORING ITEM_ID, ITEM_NAME, DESCRIPTION, PRICE, AVAILABILITY THEREBY MAKING THE DATA STRUCTURED AND CAN BE PRESENT IN FORM OF TABLES,  SO WE WILL BE USING SQL DB FOR IT.


# SEARCH SERVICE:
IT IS RESPONSIBLE FOR SHOWING ITEMS TO THE USER WHICH THEY ARE LOOKING FOR. IT USES ELASTIC SEARCH CLUSTER WHICH IS OPTIMIZED FOR FASTER READS SUPPORTING FUZZY SEARCHING AND AUTO-COMPLETION.
IT ALSO INTERACTS WITH THE INVENTORY SERVICE AND SERVICABILITY SERVICE. SEARCH SERVICE INTERACTS WITH THE INVENTORY SERVICE BECAUSE WHENEVER USER SEARCHES FOR SOME ITEM THE AVAILABILITY TAG THERE SHOWS US THE CURRENT STOCK WHICH CAN BE RETRIEVED THROUGH INVENTORY SERVICE. SEARCH SERVICE INTERACTS WITH THE SERVICABILITY SERVICE TO CHECK WHETHER THE ITEM IS SERVICABLE IN A PARTICULAR PIN-CODE OR USER'S LOCATION OR NOT. IN ORDER TO FIND USER'S LOCATION SEARCH SERVICE WILL ALSO INTERACT WITH USER SERVICE TELLING THE LOCATION OF THE USER. LET'S SAY ITEM IS SERVICABLE SO IT WILL FIND ALL AVAILABLE ROUTES FRMO WAREHOUSE TO USER'S ADDRESS AND ALSO FIND TIME TO GOING FROM SOURCE TO DESTINATION ALL WITH THE HELP OF GOOGLE MAPS SERVICE. 



# CART SERVICE:
LET'S SAY USER COMES TO WEBSITE AND SEARCHES FOR AN ITEM. SEARCH SERVICE WILL BE INVOKED AND IT WILL SHOW THEM THE ITEM. IF USER WANT TO BUY THE ITEM THEN HE WILL BE ADDING IT TO THE CART. CART SERVICE WILL BE INVOKED HERE HANDLING ADDITION/REMOVAL OF ITEMS FROM THE CART. THE DATA STORED IN CART WILL BE FREQUENTLY ACCESSED SO WE NEED TO STORE THE DATA IN REDIS CLUSTER BUT IT WOULD NOT BE PERSISTENT. SO IF USER COMES TO VIEW CART AFTER 3 4 WEEKS HE WOULD NOT BE ABLE TO ACCESS IT. HENCE WE WOULD ALSO USE SQL DB FOR PERMANENT STORAGE. WHY SQL BECAUSE THE ITEM THAT WE ARE GOING TO STORE WOULD BE VERY STRUCTURED AS WE DISCUSSED IN CASE OF INVENTORY SERVICE DB SELECTION. CART SERVICE WILL ALSO INTERACT WITH INVENTORY SERVICE TO CHECK AVAILABILITY OF STOCKS. SUPPOSE IF A USER ADD AN ITEMS TO CART BUT COMES AFTER 3-4 DAYS WHEN THE ITEM STOCK GOT OVER. SO CART SHOULD BE SHOWING IT AS NO IN STOCK BY INTERACTING WITH THE INVENTORY SERVICE FOR REAL TIME AVAILABILITY UPDATES. 


# ORDER SERVICE AND PAYMENT SERVICE:
IT IS RESPONSIBLE FOR  PLACING AN ORDER. AFTER ADDITION OF ITEM(S) IN CART WHEN USER CLICKS ON BUY ITEM/ PLACE ORDER, THE ORDER SERVICE GETS INVOKED. WE WILL BE USING SQL DB HERE FOR ORDER SERVICE. WHY? BECAUSE WE DO HAVE MULTIPLE ENTITIES AND TABLES LIKE CUSTOMER TABLE, ITEMS TABLE AND ORDER TABLE AS WELL, ETC. SO DATA WILL BE VERY STRUCTURED HERE. THERE WILL BE LOTS OF UPDATES HAPPENING IN ORDER STATUS LIKE AT SOME TIME INTERVAL ORDER STATUS WOULD BE CREATED, DELIVERED, OR EVEN CANCELLED. WE NEED TO MAKE SURE UPDATES ARE ATOMIC FORMING TRANSACTIONS AND NO PARTIAL UPDATES WHERE SQL DB'S PROVIDE THIS OUT OF THE BOX. 
WHEN A USER WILL CLICK ON PLACE ORDER BUTTON, THE ORDER SERVICE WILL CREATE AN RECORD FOR PARTICULAR ITEM AND CREATE AN ENTRY IN SQL DB WITH TAG ORDER IS CREATED. IT WILL ALSO STORE ORDER CREATION TIME AND EXPIRATION TIME IN REDIS CLUSTER. ORDER SERVICE ALSO WILL INVOKE INVENTORY SERVICE. IT WILL LOCK THE ASSIGNMENT OF AN ITEM IN INVENTORY SERVICE USING OPTIMISTIC OR PESSIMISTIC LOCKS. WE ARE DOING THIS TO ENSURE CONCURRENCY. 
AFTER LOCKING THE ASSIGNMENT WE WILL UPDATE THE DB TO REDUCE AVAILABLE STOCKS BY ONE. 

ORDER SERVICE ALSO INTERACTS WITH PAYMENT SERVICE WHICH WILL BE RESPONSIBLE FOR COMPLETING THE PAYMENT OF ORDER AFTER WHICH ORDER STATUS WOULD BE CHANGED FROM CREATED TO PLACED.

* IMPORTANT POINTS TO REMEMBER:

1. WHEN PAYMENT GETS SUCCESSFUL, PAYMENT SERVICE WILL SEND A CALLBACK EVENT TO ORDER SERVICE AND WILL SEND INFO THAT PAYMENT HAS BEEN SUCCESSFUL. ORDER SERVICE NOW MARKS AN ENTRY THAT ORDER HAS BEEN PLACED AND REMOVE THE ENTRY FROM REDIS CLUSTER(CREATION & EXPIRATION TIME). IT MARKS AN ENTRY THAT ORDER HAS BEEN PLACED AND ALSO UPDATE/DECREASE THE INVENTORY COUNT OF THE PARTICULAR ITEM SO THAT OTHER USER WOULD NOT SEE THE ITEM/PRODUCT. 

2. WHEN PAYMENT GETS FAILED, PAYMENT SERVICE WILL SEND A CALLBACK EVENT TO ORDER SERVICE AND WILL SEND INFO THAT PAYMENT HAS BEEN FAILED. ORDER SERVICE NOW MARKS AN ENTRY THAT ORDER HAS BEEN CANCELLED AND ALSO UPDATE/INCREASE THE INVENTORY COUNT OF THE PARTICULAR ITEM SO THAT OTHER USER WOULD SEE AND BUY THE ITEM/PRODUCT AND REMOVE THE ENTRY FROM REDIS CLUSTER(CREATION & EXPIRATION TIME).

3. WHEN USER WENT TO PAYMENT PAGE AND SUDDENLY CLOSES THE BROWSER, SO IN THIS CASE PAYMENT SERVICE WILL NOT SEND A CALLBACK EVENT TO ORDER SERVICE BUT AFTER SOME TIME, SO IN THIS CASE THE ENTRY WILL BE IN REDIS CLUSTER NOTIFYING THERE'S NEITHER PAYMENT SUCCESS NOR PAYMENT FAILURE. SO THE ORDER SERVICE WILL DETERMINE THAT MAYBE THE USER HAS MISTAKENLY CLOSED THE PAYMENTS PAGE AND WILL INCREASE THE INVENTORY COUNT AGAIN AND DELETE THE ENTRY FROM SQL DB AND REDIS CLUSTER. HERE RACE CONDITIONS CAN OCCUR DURING BETWEEN EXPIRATION TIME AND PAYMENT SUCCESS/FAILURE. 

* PAYMENT GETS SUCCESSFUL BEFORE EXPIRATION TIME:- LET'S SUPPOSE 10:00 AM ORDER CREATED, 10:01 AM PAYMENT SUCCESS AND ORDER PLACED, 10:05 AM EXPIRATION TIME. IN THIS CASE PAYMENT GET SUCCESSFUL BEFORE EXPIRATION TIME, SO PAYMENT SERVICE WILL SEND A CALLBACK EVENT TO ORDER SERVICE AND WILL SEND INFO THAT PAYMENT HAS BEEN SUCCESSFUL. THE ORDER SERVICE WILL THEN DELETE ENTRY IN REDIS CLUSTER AND UPDATE THE ENTRY IN SQL DB THAT ORDER HAS BEEN PLACED. 

* EXPIRATION TIME BEFORE PAYMENT GETS SUCCESSFUL:- LET'S SUPPOSE 10:00 AM ORDER CREATED, 10:05 AM EXPIRATION TIME AND 10:07 AM PAYMENT SUCCESS AND ORDER PLACED. SO AT 10:05 REDIS CLUSTER WILL TELL THAT EXPIRATION TIME HAS COME AND SENDS A CALLBACK EVENT THAT NO PAYMENT HAS NOT BEEN DONE AND ORDER NOT PLACED TO ORDER SERVICE. NOW ORDER SERVICE DETERMINES MAYBE THERE IS SOME ISSUE ON PAYMENT SIDE AND THEN INCREMENT THE ITEM ENTRY BY ONE AND THEN SEND UPDATE TO SQL DB THAT ORDER HAS BEEN CANCELLED. 
BUT NOW AT 10:07 PAYMENT SERVICE SENT CALLBACK EVENT TO ORDER SERVICE THAT PAYMENT DONE SUCCESSFULLY AND ORDER PLACED. IN THIS CASE, ORDER SERVICE CAN EITHER REFUND THE AMOUNT TO USER OR CREATE ANOTHER RECORD FOR ORDER AND WILL GENERATE A NEW ORDER ID AND STORE THE ENTRY IN SQL DB WITH TAG THAT ORDER HAS BEEN PLACED AND ADD THE USER'S AMOUNT WITH PREVIOUS ORDER WITH A NEW ORDER ID. THIS IS HOW CONCURRENCY WOULD BE MANAGED.


WHEN WE WILL SCALE OUR SYSTEM(FOR BILLIONS OF USERS), SQL DB CAN NOT BE ABLE TO STORE HUGE AMOUNTS OF DATA. USING CASSANDRA FOR ORDER SERVICE WOULD BE ALSO GREAT CHOICE. AS WE DISCUSSED, IN SQL DB WE WILL BE STORING ORDER_ID, ORDER CREATION TIME, USER'S ADDRESS(AND MORE OF USER'S INFO LIKE NAME, EMAIL ID, PHONE NO) AND ALSO DIFFERENT STATUS OF ORDERS. SO ONCE ORDER IS COMPLETED, WE WILL GRAB DATA FROM SQL DB AND STORE IT INTO CASSANDRA DB BECAUSE THIS DATA NOW WOULD BE HAVING VERY LESS NO OF QUERIES. 

* BUT HOW ARE WE GOING TO PULL DATA FROM SQL DB AND GIVE IT TO NOSQL(CASSANDRA) DB?
ANS - WE CAN USE ARCHIVAL SERVICE WHICH IS NOTHING BUT CRONE JOBS WHICH WILL SIMPLY FETCH DATA FROM SQL DB(COMPLETED ORDERS). AND THEN HISTORICAL ORDER SERVICE WOULD BE USED TO MANAGE THESE DATA. 


# RECOMMENDATION SERVICE:
NOW SERVICES LIKE SEARCH SERVICE, CART SERVICE, ORDER SERVICE, WILL PRODUCE EVENTS AND SEND THEM TO KAFKA QUEUE. THIS DATA HELPS IN RECOMMENDATION PROVIDED BY RECOMMENDATION SYSTEM. ON TOP OF KAFKA THERE WILL BE SPARK STREAMING TO PERFORM AGGREGATION AND OTHER OPERATIONS HELPING IN GENERATING RECOMMENDATION FEEDS FOR USER. 

FOR RECOMMENDATION SERVICE WE WILL BE USING CASSANDRA DB. 
THIS RECOMMENDATION SYSTEM WILL NOT BE SIMPLE AND CAN GENERATE 2 TYPES OF RECOMMENDATION:

1. GENERAL RECOMMENDATION: SPECIFIC TO A PARTICULAR USER
2. CATEGORY BASED RECOMMENDATION: LIKE SPORTS, GYM, ETC. 

IN HOME PAGE USER WILL GET TO SEE GENERAL RECOMMENDATION AND IF HE NAVIGATE TO A PARTICULAR RECOMMENDATION, CATEGORY BASED RECOMMENDATION WILL COME INTO PICTURE.
