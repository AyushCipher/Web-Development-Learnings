# PROXIMITY SEARCH ALGORITHM / BEST PROXIMITY SEARCH ALGORITHM:

1. QUAD TREE:- A QUAD TREE IS THE ONE IN WHICH PARENT NODE CAN HAVE FOUR CHILDREN. LET'S SUPPOSE WE WANT TO SEARCH A LOCATION THEN, QUAD TREE WILL DIVIDE THE WORLD MAP INTO 4 LOCATION THEN KEEP ON SUBDIVIDING THE MAP INTO FOUR QUADRANTS UTIL A LEAF NODE MARKS A SINGLE RESTAURANT OR GROUP OF RESTAURANTS NEARBY. 

BUT HERE IS A MAJOR DRAWBACK OF UNIFORMITY, WHILE DESIGNING THE QUAD TREE. WHENEVER WE ARE DESIGNING A QUAD TREE WE ASSUME DATA POINTS ARE UNIFORMLY DISTRIBUTED ACROSS THE GLOBE AND IF IS THE CASE THEN WE WILL HAVE BALANCED QUAD TREE. BUT IN REAL WORLD, RESTAURANTS OR SOME OTHER DATAPOINT DOES NOT LIE UNIFORMLY ACROSS THE GLOBE DUE TO THIS THE QUAD TREE THAT FORMS IS NOT PROPERLY HEIGHT BALANCED. SO ONE OF THE REGIONS, WHICH IS DENSELY POPULATED GET SUBDIVIDED INTO THOUSANDS OF SUBDIVISIONS SO HEIGHT OF TREE BECOMES QUITE HUGE. AND WHERE THE PLACE WHERE IT IS NOT DENSELY POPULATED, IT DOES NOT GET SUBDIVIDED. NOW LET'S SUPPOSE THAT THE QUADRANT WHERE USER IS LOCATED IN THAT NO RESTAURANT IS LOCATED SO IT BECOMES THE LEAF NODE NOW. SO THE ALGO NEEDS TO GO TO PARENT AGAIN TO SEARCH FOR WHETHER OTHER CHILDREN NODES OF SAME PARENT DO HAVE RESTAURANTS OR NOT AND IF TES THEN HOW MANY? AGAIN IF PARAMETER WAS SET TO 5KM RADIUS AND PARENT ALSO IS JUST A SMALL PART OF IT THE ALGO MOVES TO SEARCH OVER PARENT'S PARENT. AND THEN DIVIDES TO FIND SUBSEQUENT/RELEVANT RESTAURANTS IN FURTHER QUARTER SUBDIVISIONS. ALTHOUGH IT LOOKS SIMPLE BUT TO REPRESENT AND DIVIDE GLOBE INTO FOUR QUADRANTS AND FIND OUT NEARBY RESTAURANTS OR LOCATION IS QUITE TIME CONSUMING AND A SLOW APPROACH. SO WE PREFER NOT TO USE QUAD TREE TO SOLVE ANY REAL WORLD PROBLEM. SINCE QUAD TREE IS NOT A DATABASE RATHER A DATA STRUCTURE THEREFORE TO STORE IT WE ALSO NEED SOME AUXILIARY SPACE IN MEMORY. THEREFORE, WE CAN ASSUME IF THERE ARE MILLIONS OF HOTEL/RESTAURANTS LISTINGS IN OUR APP THEN WHAT CAN BE TOTAL SIZE AND DEPTH OF QUAD TREE THAT WE HAVE TO MAINTAIN. AND ALSO WHEN ANY NEW RESTAURANT GETS ADDED TO OUR DATABASE WE HAVE TO BUILD QUAD TREE AGAIN SO THAT IT CONTAINS IT IN THE CORRECT PARTITION OR QUADRANT.

ALSO WHENEVER WE ARE DESIGNING A HOTEL BOOKING APPLICATION OR DESIGNING SOMETHING REGARDING PROXIMITY SEARCH WE HAVE TO MAINTAIN 2-3 REPLICA SET OF THIS DATA-STRUCTURE. ONE IS READ(USER WILL BE READINGS/SEARCHING A DATA) AND ONE IS WRITE COPY(WHERE USER WILL BE UPDATING ADDITION OF NEW HOTELS IN SYSTEM). 

SO WE SHOULD AVOID THIS QUAD TREE FOR IMPLEMENTING THE PROXIMITY SEARCH DURING DESIGNING. WE CAN RATHER USE ITS OPTIMIZED VERSION KNOWN AS R-TREE.


2. GEO-HASH ALGORITHM(BEST-APPROACH):- IN THIS ALSO THE MAP IS DIVIDED INTO QUADRANTS AND KEEPS ON SUBDIVIDING INTO 4 PARTS UNTIL WE REACH DESTINATION. IT'S LIKE 1 MAP INTO 4 PARTS: 0,1,2,3 THEN 0 INTO 00,01,02,03 AND 1 INTO 10,11,12,13 AND SO ON..
EACH AND EVERY QUADRANT GETS DIVIDED AND ASSIGNED A NUMERIC INTEGER. IF WE KEEP ON SUB-DIVIDING INTO SMALLER GRIDS THEN THE ASSIGNED INTEGER WILL BECOME VERY HUGE INTEGER. TO REPRESENT THIS NO INTO MEANINGFUL FORM WE DO AN ENCODING CALLED AS BASE 32 ENCODING. 
WITH THE HELP OF GEO-HASHING FINDING LOCATION OF ANY RESTAURANT OR ANY LOCATION IS VERY EASY. SUPPOSE tdr1w94 IS THE LOCATION FOR DOMINOS AND ZARA IS JUST SITUATED NEARBY FOR THAT JUST CHANGE THE LAST BIT OF tdr1w94 -> tdr1w96. tdr1w9 IS BEHAVING LIKE PARENT HERE.

SO WHENEVER A NEW RESTAURANT OR HOTEL COMES TO REGISTER THEMSELVES IN OUR SYSTEM THEY PUT THE LATITUDE AND LONGITUDE OF THEIR EXACT LOCATION IN OUR APPLICATION. BASED ON THAT LATITUDE AND LONGITUDE WE CAN EASILY COMPUTE GEO-HASH LOCATION OF THAT CORRESPONDING HOTEL/RESTAURANT.

Q. HOW TO CONVERT LATITUDE LONGITUDE INTO REAL GEO-HASH?
ANS - THROUGH PRE-BUILT LIBRARIES IN WHICH WE PUT LATITUDE AND LONGITUDE OF OUR LOCATION AND TELL IT THE AMOUNT OF PRECISION WE WANT. 
* MORE PRECISION -> MORE AMOUNT OF SUBDIVISION WITHIN GRID AND LENGTH OF GEO-HASH WILL INCREASE ACCORDINGLY.  

THIS IS BETTER THAN QUAD TREE BECAUSE IN THAT WE WERE BACKTRACKING THE PARENT LEVEL ONE AT A TIME. BUT HERE IN GEO-HASH, WE ARE NOT TRAVERSING ANY REE, RATHER WE JUST CHANGE ONE BIT OF STRING TO FIND OUT NEIGHBORING LOCATION.


SCHEMA STRUCTURE THAT WE CAN USE FOR STROING INFO OF RESTAURANTS:
| Column    | Type           | Example   |
| --------- | -------------- | --------- |
| id        | INT / UUID     | 123       |
| name      | VARCHAR        | Pizza Hut |
| latitude  | FLOAT / DOUBLE | 12.9716   |
| longitude | FLOAT / DOUBLE | 77.5946   |
| geo_hash   | VARCHAR        | sgkzuts   |

TO FIND OUT ALL NEARBY RESTAURANTS WE SIMPLY WRITE A QUERY:

SELECT *
FROM restaurants
WHERE geo_hash LIKE 'sgkztus%'
OR geo_hash LIKE 'sgkztur%'
OR geo_hash LIKE 'sgkztuq%'

SINCE WE KNOW SEARCHING IS FOR NEARBY HOTELS SO WE ARE CHANGING ONLY LAST BIT.

INSERT INTO restaurants (name, location)
VALUES (
    'Taco Bell',
    ST_GeogFromText('SRID=4326;POINT(77.5946 12.9716)')
);

This inserts a restaurant named Taco Bell along with its geographical location (latitude/longitude) into the restaurants table.


* FIND RESTAURANTS WITHIN 5 KM:
SELECT *
FROM restaurants
WHERE ST_DWithin(
    location,
    ST_GeogFromText('SRID=4326;POINT(77.6000 12.9700)'),
    5000
);

This finds all restaurants within 5 km (5000 meters) of the given latitude/longitude point.


4. ELASTIC SEARCH - Elasticsearch can also be used for proximity search because it provides a special field type called geo_point, where we store the latitude and longitude of restaurants/hotels. When a restaurant is added, its location is indexed by Elasticsearch using an optimized spatial indexing structure (based on BKD trees), so Elasticsearch can quickly locate points within a particular geographical area without manually building and traversing a Quad Tree or GeoHash tree ourselves. For example, we can store Pizza Hut at latitude 12.9716 and longitude 77.5946 as a geo_point.

When a user searches for restaurants within 5 km, Elasticsearch performs a geo-distance query around the user's coordinates and returns all restaurants that fall inside that radius. Elasticsearch handles the spatial indexing and distance calculation internally, making it very suitable for applications such as food delivery, hotel booking, cab services, and location-based search, especially when we also need powerful filtering, sorting, and full-text search. Unlike PostgreSQL with PostGIS, where we need to install/enable an additional GIS extension, Elasticsearch provides geo-spatial search capabilities out of the box, so we don't need to install an external library or extension separately for basic proximity-search functionality.
