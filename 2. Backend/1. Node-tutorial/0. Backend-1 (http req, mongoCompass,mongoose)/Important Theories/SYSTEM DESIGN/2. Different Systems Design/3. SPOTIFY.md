# STREAMING SERVICE:
1. WHERE WE WILL BE STORING(FILE SYSTEM/BLOB):- 

Q. WHY NOT STORE IN FILE STORAGE?
* SCALABILITY - FILE SYSTEM SHOULD NOT BE USED SINCE DISK SPACE IS LIMITED. IN CASE, IF WE NEED 50000 GB WHAT WOULD WE DO THEN?

* DURABILITY - IF DISK/SERVER CRASHES, FILES ARE LOST.

* REPLICATION - WE WILL NEED TO MANUALLY REPLICATE FILES TO OTHER DISKS IF CRASHED.

* LATENCY - SERVING FILES TO USERS FAR FROM OUR SERVER ADDS LATENCY.

* BACKUPS - NO BUILT IN VERSIONING OR BACKUP MECHANISMS.

* NO CDN - NO CACHING, NO GEO-REPLICATION, ETC. 


Q. WHY TO STORE IN BLOB STORAGE?
* MASSIVE SCALE - STORE BILLIONS OF OBJECTS, NO SIZE LIMIT PER PROJECT.

* HIGHLY DURABLE - 99.99999% DURABILITY. THEY ALSO PROVIDE FEATURE OF DATABASE REPLICATION.

* GLOBALLY AVAILABLE - INTEGRATED WITH CDN'S(CLOUDFRONT/AKAMAI); FAST DELIVERY OF STATIC CONTENTS.

* VERSIONING - CAN STORE MULTIPLE VERSIONS OF FILE.

* ACCESS CONTROL - PRE-SIGNED URLS'S, ROLE BASED ACCESS.

* STREAMING SUPPORT - RANGE REQUESTS, PROGRESSIVE DELIVERY OF AUDIO CHUNKS.

* PAY AS YOU GO - ONLY PAY FOR WHAT YOU STORE AND SERVE.




# Q. JUST FOR UNDERSTANDING LET'S SEE HOW FILES ARE GONNA BE STORED IN FILE SYSTEM AND HOW BACKEND SERVER PROCESSES IT?
ANS - USER FILLS A FORM AND UPLOADS AUDIO.MP3 FILE AS WELL AS MULTIPART DATA. THIS IS SENT TO BACKEND SYSTEM WHICH THEN PARSE IT AND WILL STORE IT INTO SMALL BINARY FILES AND SENT THIS TO FILE SYSTEM. 


WE STORE THE DATA IN BLOCKS IN FILE SYSTEM. LET'S SAY SONG SIZE IS 4MB AND BLOCK SIZE IF 4KB. WE WOULD THEN REQUIRED 1000+ BLOCKS FOR STORING THIS AUDIO FILE. THE DATA IN BLOCKS ARE NOT STORED CONSECUTIVELY, RATHER ANYWHERE BUT CONNECTED TOGETHER LIKE IN CASE OF LINKED LIST. 



# Q. JUST FOR UNDERSTANDING LET'S SEE HOW FILES ARE GONNA BE STORED IN BLOB STORAGE?

* BRUTE FORCE APPROACH - USER/ARTIST WILL FILL A FORM IN WHICH HE WILL SEND HIS MUSIC FILE IN FORM OF MULTIPART FORM DATA. IT IS SENT TO BACKEND SERVER WHICH ON RECEIVING FILES CONVERTS IT TO BINARY FORMAT AND THEN THESE FILES ARE STORED IN S3 STORAGE AS OBJECTS AND IN CDN TO ACCESS IT FAST TO REDUCE LATENCY. S3 STORAGE WILL CREATE A PARTICULAR URL FOR THE PARTICULAR FILE AND WILL SEND IT TO BACKEND SERVER. THE BACKEND SERVER SENDS THIS URL TO SQL DATABASE.


NOW, WHEN CLIENT REQUESTS(GET) FOR A SONG (HAVING SONGID) FROM THE SERVER, THE SERVER SENDS SONGID TO THE SQL DATABASE TO FIND OUT THE URL CONTAINING THE SONGID AND IF FOUND RETURNS THE URL TO THE SERVER WHICH RETURNS THE PRE-SIGNED URL TO THE CLIENT. NOW CLIENT SENDS PRE-SIGNED URL TO S3 STORAGE OR CDN AND THEN THE AUDIO TRACK STARTS DOWNLOADING AND SENT TO CLIENT.
WHEN USER WILL CLICK ON THE PLAY BUTTON THEN BUFFERED CHUNKS OF THE AUDIO WILL BE PLAYED. 



2. HOW WE WILL BE STORING:-

* RANGE REQUESTS - SAME APPROACH AS FOR STORING IN S3 STORAGE, CDN AND DB. 

BUT HERE IN BRUTE FORCE METHOD, IS USER WANTS TO JUMP FROM 1ST MINUTE OF SONG TO 3RD MINUTE HE MIGHT NOT BE ABLE TO DO IT SINCE THE BUFFER MAY NOT HAVE BEEN DOWNLOADED YET. BUT HERE THE CLIENT WILL FETCH ONLY THE BYTES THAT ARE NEEDED. 
EXAMPLE: GET/songs/song123.mp3
Range: bytes=100000-200000, we use http because it supports fetching from specific bytes ranges. 

NOW IS USER WANTS TO SEEK FROM 1ST TO 3RD MINUTE OF THE SONG, THEN HE WILL PROVIDE A SPECIFIC BYTE RANGE BELONGING TO THE SPECIFIC 4TH MINUTE(2000-4000) IN THE HTTP REQUEST CORRESPONDING TO WHICH S3 STORAGE/CDN WILL SEND SPECIFIC CHUNKS OF DATA RELATED TO THE RANGE. BU IT IS ALSO NOT AN OPTIMIZED APPROACH, BECAUSE IF WE ARE DOING THIS IN AAN AREA WHERE NETWORK CONNECTIVITY IS VERY POOR THEN WE WILL NOT BE ABLE TO PLAY THE SONG. 


THIS LEADS US TO:
* ADAPTIVE BITRATE STREAMING - SERVER RUNS FFMPEG( A SOFTWARE THAT HANDLES VIDEO, AUDIOS, IMAGES) TO TRANSCODE THE AUDIO FILE INTO MULTIPLE QUALITY VERSIONS. AFTER FFMPEG WORKED, WE WILL GET DIFFERENT AUDIO VERSIONS OF THE FILE LIKE 90KBPS, 160KBPS, 320KBPS. AAC(ADVANCED AUDIO CODING - AUDIO COMPRESSION FORMAT) IS THE SUCCESSOR OF MP3 BUT A FORMAT. AFTER DIVING song_96.aac INTO segment_000.aac,segment_001.aac,segment_002.aac USING FFMPEG AND EACH SEGMENTS CONTAINING SMALL CHUNKS OF FILE(SAY EACH SEG. CONTAINING 5 SECONDS OF AUDIO). IN ORDER TO MANAGE THESE SEGMENTS OR DIFFERENT VERSIONS OF THE SONG, WE NEED A MANIFEST(song_96.m3u8, song_160.m3u8) FILE LIKE A PLAYLIST. NOW AFTER DIVING THE FILES INTO DIFFERENT SEGMENTS, VERSIONS AND MANIFEST FILES IN S3 STORAGE AS OBJECTS. 



3. HOW WE WILL BE FETCHING:

FLOW - CLIENT HITS GET REQ WITH SONG_ID, TO THE SERVER. THE SERVER THEN SEARCHES THE CORRESPONDING SONG_ID WITH THE URL PARAMETERS IN THE DATABASE. IF FOUND ONE, IT RETURNS THE PRE-SIGNED URL TO THE SERVER WHICH THEN RETURNS IT TO THE CLIENT. THE CLIENT HAVING THE PRE-SIGNED URL REQUESTS THE MP3 FILE FROM S3 STORAGE AND RECEIVES IT CHUNK BY CHUNK. NOW IF NETWORK PROBLEM ARISES, THEN IT SERVES THE song_98.m3u8 MANIFESTO FILE CONTENT WHICH IS COMPARATIVELY POOR BUT IF USER TOOK PREMIUM SUBSCRIPTION AND HAVING A GOOD NETWORK THEN HIGH-QUALITY(song_320.m3u8) MANIFEST DATA FILES WOULD BE SERVED. DEPENDING UPON NETWORK, CLIENT WILL AUTOMATICALLY SWITCH TO SEGMENTS OF DIFFERENT MANIFESTO FILES. 


4. HOW PLAY/PAUSE/SEEK/SKIP WILL FUNCTION:
WHEN USER CLICKS ON PLAY BUTTON, THEN PLAYER STARTS FETCHING DIFFERENT SEGMENTS FROM S3 STORAGE OR CDN BY SENDING SIGNED URL TO S3/CDN AFTER WHICH THEY SEND DIFFERENT SEGMENTS(6-7 AT ONCE) TO PLAYER/USER. IT WILL NOT ONLY REQUEST SOME SEGMENTS BUT 6-7 SEGMENTS AT ONCE IN SINGLE REQ, AND SEGMENTS WHICH ARE NOT RUNNING WILL BE STORED IN MEMORY OF CLIENT AND WILL PLAY ONLY REQUIRED SEGMENTS. 


WHEN USER CLICKS ON PAUSE BUTTON, THEN IN THIS CASE THE USER WILL STOP REQUESTING FROM S3/CDN AND THE REQUESTED SEGMENTS WHICH WERE STORED IN MEMORY OF CLIENT WILL STAY AS IT IS.


WHEN USER CLICKS ON SKIP BUTTON, THEN IN THIS CASE ALL THE DIFFERENT SEGMENTS OR MANIFEST FILES STORED IN MEMORY/BUFFER WILL BE VANISHED/FLUSHED AND NEW MANIFEST FILES, NEW DIFFERENT SEGMENTS WITH NEW BITRATE FOR NEW SONGS WILL BE FETCHED FROM S3/CDN ACCORDING TO USER'S PLAN(SUBSCRIPTION). 


WHEN USER JUMPS ON TO SOME OTHER PART OF THE SONG, THEN IN THIS CASE CLIENT WILL IDENTIFY WHICH SEGMENT WE NEEDED. LETS SAY USER WANTS TO JUMP FROM 1ST TO 3RD MINUTE OF THE SONG, THE AUDIO PLAYER/CLIENT WILL IDENTIFY ALL SEGMENTS AVAILABLE IN 3RD MINUTE AND WILL REQUEST THOSE SEGMENTS TO S3/CDN IN RESPONSE OF WHICH THEY SEND SEGMENTS FOR PARTICULAR SIGNED URL.
