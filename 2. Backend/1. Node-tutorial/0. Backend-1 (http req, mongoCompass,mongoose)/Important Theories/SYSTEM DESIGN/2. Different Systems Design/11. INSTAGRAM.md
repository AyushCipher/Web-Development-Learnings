# FLOW:-

# USER SERVICE:
IT STARTS FROM LOGIN UI WHEN USER LOGS IN THE REQUEST IS FORWARDED TO USER SERVICE POWERING LOGIN AND SIGNUP FUNCTIONALITY. IT IS ALSO A SOURCE OF TRUTH FOR USER RELATED INFORMATION. IF SOMEONE WANTS TO CHANGE USERNAME, EMAIL OR PHONE NO WILL ALL BE MANAGED BY USER SERVICE. IT WOULD BE HAVING BOTH POST API'S FOR UPDATING USER'S INFORMATION AND GET API'S TO GET THE USER'S INFORMATION. IT USES SQL DB BECAUSE USER RELATED DATA IS VERY STRUCTURED AND THOUGH CAN BE REPRESENTED IN FORM OF TABLES(ROWS & COLS). IT WOULD ALSO USE REDIS AS USER INFORMATION DATA IS FREQUENTLY ACCESSED AND USER RELATED INFO WILL NOT GOING TO BE CHANGED VERY FREQUENTLY.


# GRAPH SERVICE:
IF USER1 WANTS TO FOLLOW USER2, OR WANTS TO FETCH FOLLOWERS OF USER2 IN THAT CASE ALL POST API'S AND GET API'S WOULD BE PROVIDED BY GRAPH SERVICE. IT WILL PROVIDE BULK GATE API'S TO FIND MUTUAL CONNECTIONS. SO INSTEAD OF CALLING GRAPH SERVICE AND USER SERVICE FOR EACH AND EVERY USER, IT WILL FETCH ALL FRIENDS/FOLLOWERS IN A SINGLE GO REDUCING LATENCY AND SAVING TIME. IT ALSO SITS ON TOP OF SQL DB BECAUSE HERE ALSO MILLIONS OF DATA WILL BE VERY WELL STRUCTURED. 
HERE THE SQL DB WILL BE MANAGING MORE DATA AS COMPARED TO USER SERVICE SQL DB FOLLOWERS AND FOLLOWING AS WELL. WE ALSO CONSIDER REDIS FOR THIS DATA OF FOLLOWERS AND FOLLOWING BECAUSE ITS VERY FREQUENTLY ACCESSED. WE WILL BE DOING THIS WITH KEY AS USER_ID AND VALUE AS OBJECT OF FOLLOWING AND FOLLOWERS.



Q. HOW USER WILL HANDLE UPLOAD OF POST OR PICTURE?

USER WILL GO OT UPLOAD UI FIRST IN WHICH HE WILL ADD A PICTURE AND SOME DESCRIPTION AND WILL HIT ON POST BUTTON. THIS WILL INVOKE THE POST INGESTION SERVICE. IT WILL IDENTIFY THE POST TYPE(WHETHER IT CONTAINS IMAGE OR VIDEO OR LONG_URL) AND THEN ACCORDINGLY IT SENDS DATA TO DIFFERENT SERVICES. LIKE IF THE POST CONTAINS IMAGE/VIDEO THEN IT SENDS DATA TO ASSET SERVICE (THIS ASSET SERVICE IS NOTHING BUT BASED ON NETFLIX SYSTEM DESIGN). BUT IF THE POST CONTAINS LONG_URL THEN IT WILL FORWARD IT TO TINY_URL SERVICE. NOW, TINY_URL SERVICE WILL GENERATE A SHORT UNIQUE URL FOR THAT PARTICULAR LONG_URL AND ADD AN ENTRY TO THE DATABASE. THEN IT WILL PROVIDE THE SHORT_URL TO POST INGESTION SERVICE / USER. NOW THE UPLOADED MEDIA IS MANAGED BUT THE DESCRIPTION PLAIN TEXT WOULD ALL BE STORED IN NOSQL(CASSANDRA) DB BY THE POST INGESTION SERVICE. 
ALSO THE POST INGESTION SERVICE WILL GENERATE A UNIQUE POST_ID FOR A POST AND SEND IT TO KAFKA QUEUE. 

# POST INGESTION SERVICE: 
IT IS RESPONSIBLE FOR SAVING THE POSTS TO DIFFERENT DATA STORES. BUT DOES NOT PROVIDE ANY SUCH API'S SO FETCH THE POSTS. 



# POST SERVICE:
IT IS RESPONSIBLE FOR FETCHING THE POSTS AND PROVIDES US GET API'S. IT IS SITTING ON TOP OF CASSANDRA DB. IT IS ALSO RESPONSIBLE FOR GENERATING TIMELINE OF USERS.

* Q. NOW WHEN SOME USER WILL COME TO HOME(USER'S HOME PAGE) OR USER TIMELINE(PROFILE PAGE OF SOME OTHER USER - POSTS,USERNAME,BIO), WHAT ARE THINGS THEY WILL SEE?

SUPPOSE IF USER1 WILL VISIT THE TIMELINE OF USER2. HE WILL SEE ALL THE POSTS MADE BY USER2, USER_NAME OF USER2 AS WELL AS THEIR BIO, ETC. USER1 WILL INVOKE TIMELINE SERVICE TO ASK THE DETAILS OF POSTS, USERNAME, BIO TO POST SERVICE. NOW POST SERVICE WILL SEND USER2_ID TO CASSANDRA DB, AND FETCH ALL POSTS MADE BY USER2. AGAIN, TIMELINE SERVICE WILL MANAGE AND ARRANGE THEM AND SEND THIS DATA TO USER TIMELINE. 

QUERY TO FETCH SOME USER'S TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = USER2

QUERY TO FETCH MY OWN TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = OWN_USER_ID

QUERY TO FETCH HOME TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = <LIST_OF_FOLLOWING>

NOW IF USER GO TO HOME PAGE, WE WILL SEE THE POSTS OF USERS THAT WE FOLLOW. IN THIS CASE, WE CAN FOLLOW BRUTE FORCE APPROACH. FROM HOME TIMELINE UI PAGE, REQUEST GOES TO TIMELINE SERVICE. IN ORDER TO GENERATE HOME TIMELINE, TIMELINE SERVICE MUST FIND OT ALL USERS THAT USER1 FOLLOWS. IT WILL THEN CALL GRAPH SERVICE AND THROUGH IT WILL BE FETCHING ALL DETAILS OF USERS THAT USER1 FOLLOWS. IT WILL FETCH USER_ID'S OF ALL THOSE USERS WHO USER1 FOLLOWS AND WILL SEND IT TO POST SERVICE. NOW POST SERVICE WILL FETCH ALL DIFFERENT POSTS MADE BY USERS THAT USER1 FOLLOWS FROM CASSANDRA DB. THIS DATA IS THEN SENT TO TIMELINE SERVICE WHICH ARRANGES AND SORT THESE DATA ON BASIS OF LATEST POST AND SEND THIS TO HOME TIMELINE. 

BUT THE PROBLEM IN BRUTE FORCE ARISES WHEN A USER FOLLOWS 1000 PEOPLE. IN THAT CASE WE WILL BE QUERYING CASSANDRA DB AGAIN AND AGAIN FOR THIS MUCH AMOUNT OF USER THAT TOO SUPPOSE 6-7 TIMES A DAY WILL SLOW DOWN THINGS AND INCREASE LATENCY. 
SO INSTEAD OF THIS BRUTE FORCE TECHNIQUE, WE WILL CACHE THE HOME TIMELINE OF ACTIVE USERS. SINCE WE KNOW INSTAGRAM IS READ HEAVY SYSTEM, IT BECOMES GOOD APPROACH TO CACHE SOME INFORMATION.


# POST PROCESSOR SERVICE:
WE ALREADY KNOW THAT POST INGESTION SERVICE WILL SEND AN EVENT TO KAFKA( KEY(USER1)-> VALUE(POST1)). NOW, WE WILL BE HAVING POST PROCESSOR SERVICE WHICH WILL GRAB AN EVENT THAT USER1 HAS MADE A NEW POST1 AND WILL FIND OUT ALL FOLLOWERS OF USER1 (BY TALKING TO GRAPH SERVICE) AND CREATE A TIMELINE FOR THEM SUPPOSE USERS USER4, USER5, USER6 HAVING POST OF USER1. WE WILL BE CACHING THIS INFORMATION IN REDIS WHERE KEY IS USER_ID AND VALUE WILL BE POST_ID. NOW, IF USER4 COMES AND VIEWS HOME TIMELINE UI THEN IT WILL INVOKE THE TIMELINE SERVICE WHICH WILL FIRST CHECK IN REDIS DO WE HAVE AN ENTRY IN REDIS. REDIS WILL PROVIDE RESPONSE BY GIVING DATA TO TIMELINE SERVICE WHICH WILL RETURN DATA TO BE DISPLAYED IN TIMELINE UI. 

* BRUTE FORCE APPROACH FLOW:- USER4 -> TIMELINE SERVICE -> GRAPH SERVICE -> FIND ALL FOLLOWING -> POST SERVICE -> CASSANDRA -> FETCH THOUSANDS OF POSTS -> SORT(TIMELINE SERVICE) -> RETURN

* POST PROCESSOR SERVICE IMPROVISED FLOW:- USER4 -> TIMELINE SERVICE -> REDIS -> PRE-COMPILED HOME TIMELINE -> USER4



WE CAN NOTICE HOW OUR FLOW DECREASED. WE CALL THIS TECHNIQUE AS FAN-OUT-ON WRITE. 
* Fan-out on Read: User opens Home Timeline → system finds everyone they follow → fetches their posts → builds the timeline at read time.

* Fan-out on Write: User creates a post → Post Processor finds their followers → pushes/adds that post to each follower's timeline at write time → stores it in Redis.

NOTE:- WE WILL NOT STORE THE HOME TIMELINE OF ALL THE USERS INSTEAD WE STORE FOR THE USERS WHO ARE ACTIVE(ACCESSED INSTAGRAM IN LAST 3 DAYS). 



Q. HOW WILL SYSTEM FIND OUT WHETHER USER IS A ACTIVE OR PASSIVE USER?
ANS - TIMELINE SERVICE WILL ASK THE USER PROFILE SERVICE TO GET THE INFORMATION ABOUT LAST LOGIN. IF ACTIVE THEN, INFO WILL BE FETCHED/QUERIED FROM REDIS CACHE. 


SUPPOSE IF USER4 IS PASSIVE USER(NOT ACCESSED INSTAGRAM IN LAST 3 DAYS), THEN WE ARE NOT GOING TO FIND HOME TIMELINE IN REDIS. 
RATHER IT WIL FOLLOW THE BRUTE FORCE KIND OF APPROACH IN WHICH THE USER4 COMES TO THE HOME TIMELINE AND HIS REQUEST WILL GO TO TIMELINE SERVICE WHICH WILL FURTHER PASS THIS REQUEST TO GRAPH SERVICE FINDING WHO USER4 FOLLOWS. THE GRAPH SERVICE WILL SEND THE USER_ID OF USERS WHOM USER4 FOLLOWS TO TIMELINE SERVICE. NOW, TIMELINE SERVICE WILL QUERY POST SERVICE ASKING TO PROVIDE ALL POSTS MADE BY USERS WHOM USER4 FOLLOWS. POST SERVICE WILL QUERY CASSANDRA DB AND FIND OUT POSTS MADE BY THOSE USERS AND PASSES IT TO POST SERVICE WHICH FURTHER PASSES IT DOWN TO TIMELINE SERVICE WHICH THEN ARRANGE AND SORT DATA BASED ON LATEST POST AND FORWARDS IT TO HOME TIMELINE PAGE. ALSO TIMELINE SERVICE ALSO SENDS THIS DATA TO REDIS AS USER4 HAS BECOME ACTIVE USER NOW. 


Q. HOW DO WE MANAGE FOR CELEBRITIES?
SUPPOSE IF USER6(CELEBRITY) HAVING 75 MILLION+ FOLLOWERS UPLOADS A POST THEN ARE WE GOING TO UPDATE IT TO HOME TIMELINE OF 75M+ USERS FOR A SINGLE UPDATE. OF COURSE, NO. 

LETS SAY USER4 IS AN ACTIVE USER AND HE FOLLOWS BOTH USER1 AND USER2. USER2 IS NORMAL USER WILL 60 FOLLOWERS SO HIS NEW POST WILL BE FETCHED AND SHOWN IN HOMEPAGE OF USER4 USING THE REDIS CACHE METHOD. BUT IN CASE OF USER1 HAVING 75M+ FOLLOWERS, FROM THE HOME PAGE, TIMELINE SERVICE IS INVOKED WHICH INVOKES THE GRAPH SERVICE TO FETCH ALL CELEBRITIES THAT USER4 FOLLOWS AND REQUESTS THE POST SERVICE TO RETRIEVE NEW POST INFO FROM CELEBRITY THROUGH CASSANDRA DB. WHEN CASSANDRA DB RETURN THE DATA(POST_ID) TO POST SERVICE, IT SERVES THE DATA TO TIMELINE SERVICE. TIMELINE SERVICE HAVING ACCESS OF POST FROM USER2 THROUGH REDIS AND POST FROM USER1(CELEBRITY) IN THIS WAY AND COMBINES THEM TO RETURN THIS OUTPUT TO USER4. 


* REDIS CAN BECOME A BOTTLENECK HERE:- 
REDIS WILL STORE TODAY'S DATA IN STORAGE.
FOR EVERYTHING IN PAST, WE USE ARCHIVAL SERVICE WILL FETCH ALL PAST DATA FROM REDIS LIKE HOME TIMELINE BY RUNNING A CRON JOB AND FETCH HOME TIMELINE OF DIFFERENT USERS AND THEN STORE IT IN NOSQL DB AND CLEARS THE CACHE. 



# SEARCH SERVICE:
WHEN USER SEARCHES ABOUT A SPECIFIC USER THEN HE ACCESSES THE SEARCH UI WHICH THROUGH HELP OF LOAD BALANCERS INVOKES THE SEARCH SERVICE WHICH THEN INVOKES ELASTIC SEARCH CLUSTER(FOR FUZZY SEARCHING AND AUTO COMPLETION). IT WILL SERVE BOTH GET AND POST API REQ, GET FOR RETRIEVING THE REQUEST AND POST FOR SUPPOSE ANY NEW POST IS ADDED TO THE APPLICATION THEN SINCE POST INGESTION SERVICE SENT THE EVENT THROUGH KAFKA THIS WOULD BE CONSUMED BY SEARCH SERVICE TO SHOW THE LATEST RESULTS RELATED TO PARTICULAR KEYWORDS .


# LIKE SERVICE:
IT IS RESPONSIBLE FOR PUTTING A LIKE ON A PARTICULAR POST AND GETTING NO OF LIKES ON A PARTICULAR POST. WE WILL BE STORING USER_ID OF USER WHO LIKED THE POST, AND THE POST_ID OF POST BEING LIKED. CASSANDRA DB WOULD BE USED TO STORE THIS INFO. REDIS CAN BE CONSIDERED FOR LIKE SERVICE. WHENEVER A POST IS SHOWN, NO OF LIKES ARE ALSO DISPLAYED, WHICH IS POWERED BY REDIS.  


# COMMENT SERVICE:
IT IS RESPONSIBLE FOR PUTTING A COMMENT ON A PARTICULAR POST AND GETTING NO OF COMMENT ON A PARTICULAR POST. WE WILL BE STORING USER_ID OF USER WHO COMMENTED ON THE POST, AND THE POST_ID OF POST BEING COMMENTED AS WELL AS THE COMMENT.  CASSANDRA DB WOULD BE USED TO STORE THIS INFO. REDIS CAN BE CONSIDERED FOR COMMENT SERVICE. 


# ACTIVITY LOG SERVICE:
WHATEVER POST ON WHICH USER IS COMMENTING, LIKING AS WELL AS THE SEARCHES HE MAKE WILL BE SENT AS EN EVENT OT KAFKA. THIS KAFKA WILL SEND THIS DATA TO ACTIVITY LOG SERVICE WHICH WOULD BE POWERED BY NOSQL DATABASE(HAVING 3 COLS LIKE USERID, POST, ACTION), WHICH WOULD HELP IN RECOMMENDATION. IT WILL ALSO POWER SOME OF POST API'S TO STORE SOME OF USER'S ACTION IN DB AS WELL AS GET API'S TO 
ACCESS USERS ACTIVITY.

ANS- IN CASE OF NO INTERACTIONS WE WILL REMOVE THE POST FROM CDN AND WILL UTILIZE IT FOR STORING SOME OTHER POSTS.
