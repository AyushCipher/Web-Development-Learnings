# FUNCTIONAL REQUIREMENTS:
1. SEARCH FOOD ITEMS AND RESTAURANTS
2. ADD/REMOVE ITEMS FROM CART
3. VIEW THEIR PAST ORDERS

# NON-FUNCTIONAL REQUIREMENTS:
1. LOW LATENCY(SEARCH, RECOMMENDATION)
2. HIGH AVAILABILITY

# SERVICES:
1. RECOMMENDATION
2. SEARCHING
3. INVENTORY 
4. PAYMENT 
5. CART


FLOW:
STARTING: ONBOARDING SERVICE FOR ONBOARDING DIFFERENT RESTAURANTS AS WELL AS THEIR MENU TO BE LISTED IN SWIGGY. IT WILL SEND THIS DATA TO KAFKA AND WHICH WILL FURTHER SEND THIS EVENT TO SEARCH AND INVENTORY SERVICE. IT WILL SEND DATA TO SEARCH SERVICE SINCE THE RESTAURANT LISTED COULD NOW BE  SEARCHED AND ITEMS FROM IT CAN BE ORDERED SPECIFICALLY. EVENT SENT TO INVENTORY SERVICE ALSO BECAUSE IT IS THE SOURCE OF TRUTH. LET'S SUPPOSE SOME ITEMS ARE NOT AVAILABLE FOR A PARTICULAR DAY THEN THIS COULD BE GET KNOWN BY THE INVENTORY SERVICE.

NOW, WHEN THE UI MAKES REQ OR WANTS TO SEARCH A FOOD ITEM THEN REQ WILL GO TO SEARCH SERVICE WHICH WILL SEARCH THE ELASTIC SEARCH CLUSTER(PROVIDES FUZZY SEARCHING AND AUTO-COMPLETION FUNCTIONALITIES) FOR USER'S REQUEST. ALSO THE SEARCH SERVICE WILL ALSO TALK TO THE INVENTORY SERVICE TO FIND OUT WHAT ITEMS ARE AVAILABLE AND WHAT ARE NOT TELLING USER WHILE SEARCHING THAT THE ITEM IS CURRENTLY OUT OF STOCK MAKING USER EXPERIENCE GOOD. 

SEARCH SERVICE ALSO TALKS WITH THE USER SERVICE BECAUSE ALL THE INFORMATION RELATED TO USER LIKE NAME, ADDRESS, ETC . WE WANT TO KNOW THE USER'S CURRENT LOCATION DUE TO WHICH SEARCH SERVICE TALKS WITH USER SERVICE TO FIND OUT WHETHER THE SEARCHED ITEM BY USER IS DELIVERABLE AT HIS LOCATION OR NOT. USER SERVICE IS SOURCE OF TRUTH FOR USER RELATED INFO LIKE NAME, EMAIL, PHONE NO, ADDRESS, ETC. WE WILL BE STORING ALL INFO OF USER IN SQL DATABASE(MYSQL) BECAUSE THE DATA IS VERY STRUCTURED AND IT CAN BE PRESENTED IN FORM OF TABLES. IT ALSO USES CACHE BECAUSE MANY TIMES LOT OF OTHER SERVICES NEED INFORMATION ABOUT A PARTICULAR USER. SO, WE HERE CACHE MEMORY IMPLEMENTED THROUGH REDIS. 

SEARCH SERVICE ALSO TALKS WITH THE CART SERVICE. AS WE KNOW USER CONSTANTLY ADDS/REMOVES ITEMS FROM THE CART SO IS IS FREQUENTLY ACCESSED HENCE WE USE CACHING HERE AS WELL THROUGH REDIS. FOR CART SERVICE, WE USE NOSQL DATABASE AS WE ARE MANAGING HUGE AMOUNTS OF DATA AND FOR EACH RESTAURANT ITEM THERE CAN BE SPECIFIC PROPERTIES LIKE FOR PIZZA(SMALL, MED, LARGE), BURGER(GRILLED, CHEESY), COFFEE(LATTE, CHOCOLATE, ESPRESSO) AND MUCH MORE. 


WE NEED PERMANENT STORAGE ALSO WHICH CAN BE POSSIBLE USING NOSQL DATABASE BECAUSE FOR SUPPOSE WE HAVE LOGGED IN THROUGH OTHER DEVICE WI SAME CREDENTIALS THEN WE SHOULD BE SEEING THE CART ITEMS AS IT IS LIKE IN PREVIOUS DEVICE. 

CART SERVICE ALSO INTERACTS WITH THE INVENTORY SERVICE(SOURCE OF TRUTH) HELPING IT KNOW WHETHER THE ITEMS IS CURRENTLY IN STOCK OR NOT. LET'S SAY I ADDED 4-5 ITEMS ON TUESDAY, AND ORDERING ON WEDNESDAY. IT MAY HAPPEN THAT SOME ITEMS BECAME UNAVAILABLE ON THE MENU. HERE THE INVENTORY SYSTEM WILL HELP IT VALIDATE AGAIN THAT THESE PARTICULAR ITEMS ARE NOT AVAILABLE NOW. 


NOW WHEN USER CLICKS ON PLACE ORDER BUTTON, THE ORDER SERVICE WILL BE INVOKED. SQL DATABASE WILL BE USED FOR ORDER STORAGE BECAUSE THEY WILL BE GOING TO BE VERY STRUCTURED HAVING ORDER ID, CUSTOMER NAME, CUST_ADDRESS, ETC THAT CAN BE REPRESENTED WELL WITH TABLES. SINCE EVERYTIME THE ORDER STATUS MAY ALSO CHANGES/UPDATES DUE TO WHICH IT BECOMES NECESSARY TO MAINTAIN ATOMICITY AND CONSISTENCY AND ALSO THEY CAN FORM TRANSACTIONS DUE TO WHICH SQL WOULD BE BEST CHOICE. 

WHEN USER CLICKS ON PLACE ORDER BUTTON, AN ENTRY HAS BEEN CREATED STORING THE CREATED ORDER AND STORING ORDER CREATION TIME, ORDER EXPIRATION TIME IN REDIS CLUSTER. NOW ORDER SERVICE WILL REDIRECT USER TO PAYMENT SERVICE. IF PAYMENT IS SUCCESSFUL THEN IT WILL CREATE AN CALLBACK EVENT TO ORDER SERVICE THAT PAYMENT IS SUCCESSFUL. SO WE WILL UPDATE ENTRY IN DATABASE THAT ORDER HAS BEEN PLACED AND DELETE ENTRY FROM REDIS. IF PAYMENT NOT MADE SUCCESSFUL, THEN PAYMENT SERVICE WILL CREATE AN CALLBACK EVENT TO ORDER SERVICE THAT PAYMENT IS NOT MADE/FAILED/CANCELLED. SO ORDER SERVICE MARKED ENTRY IN DATABASE THAT ORDER HAS BEEN CANCELLED, AND WE WILL REMOVE ENTRY FROM REDIS AS WELL. 

NOW LETS SAY USER WENT TO PAYMENT GATEWAY PAGE, AND BECAUSE OF SOME REASON HE CLOSED THE BROWSER. IN THIS CASE THE PAYMENT SERVICE WILL NOT BE ABLE TO SEND AN EVENT TO THE BROWSER. IN THIS CASE, REDIS WILL BE VERY HELPFUL TO RESOLVE ISSUE. LET'S SAY ORDER HAS BEEN CREATED AT 10:00 AM AND EXPIRED AT 10:05 AM AND THIS ENTRY WOULD ALSO BE STORED IN REDIS. AFTER ORDER HAS BEEN CREATED, ORDER SERVICE WILL INVOKE THE PAYMENT SERVICE FOR MAKING PAYMENT, AND THERE WOULD BE NO CALLBACK EVENT SENT BY PAYMENT SERVICE UP TO 10:05 AM THEN IN THIS CASE REDIS WILL UPDATE ORDER SERVICE THAT THERE'S STILL ENTRY IN REDIS WHICH WILL HELP ORDER SERVICE DETERMINE THAT THERE HAS BEEN SOME ISSUE WHILE PAYMENT. SO THIS ENABLES ORDER SERVICE THE MARK THE ENTRY IN SQL DATABASE THAT ORDER IS CANCELLED. 

ON SUCCESSFUL PAYMENT MADE, ORDER SERVICE WILL SEND TWO EVENTS TO TWO DIFFERENT SERVICES: 
1. RESTAURANT SERVICE(AFTER  RECEIVING CONTACT AND ORDER DETAILS OF THE USER, IT WILL CONTACT ONE OF RESTAURANTS[MAYBE DISH SPECIFIC OR ANY RESTAURANT])

2. DELIVERY SERVICE(BECAUSE WE WILL ALSO HAVE TO FIND CLOSEST AVAILABLE DRIVERS BETWEEN RESTAURANT AND USERS) 


# RECOMMENDATION SERVICE:
