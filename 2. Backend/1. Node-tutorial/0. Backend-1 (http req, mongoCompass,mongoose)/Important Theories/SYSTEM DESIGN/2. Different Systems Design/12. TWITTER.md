# USER SERVICE:
AS USER COMES TO APPLICATION, USER SERVICE WILL BE INVOKED AND THEN USER WILL BE STORING USER RELATED INFO LIKE USERNAME, PASSWORD, EMAIL_ADDRESS, PHONE NO, AND OTHER INFORMATION. IT WIL BE SOURCE OF TRUTH FOR THE USER. IT WILL BE ALSO HAVING FUNCTIONALITY OF LOGIN AND SIGNUP AND RESPONSIBLE FOR USER AUTHENTICATION. OTHER SERVICES WILL TALK TO USER SERVICE FOR USER RELATED DETAILS. WE ARE USING SQL DB HERE BECAUSE USER RELATED DATA IS VERY STRUCTURED AND THOUGH CAN BE REPRESENTED IN FORM OF TABLES(ROWS & COLS). IT WOULD ALSO USE REDIS AS USER INFORMATION DATA IS FREQUENTLY ACCESSED AND USER RELATED INFO WILL NOT GOING TO BE CHANGED VERY FREQUENTLY. WE ALSO KNOW OUR SYSTEM IS READ HEAVY THEN IT WILL BE A GOOD APPROACH TO PRE COMPUTE OR CACHE INFO.

IF USER REQUESTS HIS PROFILE DATA THEN DATA WOULD BE FIRST SEARCHED IN REDIS CLUSTER IF NOT PRESENT THERE THEN INFO WILL BE OBTAINED FROM SQL DATABASE AND STORED IN REDIS CLUSTER FOR FUTURE FREQUENT INTERACTIONS. 

* REDIS CLUSTER DETAILS:- USER_DETAILS, FOLLOWERS, FOLLOWING, TYPE(ACTIVE, PASSIVE), LAST ACCESS TIME( TO IDENTIFY ACTIVE/PASSIVE USAGE)


# GRAPH SERVICE:

IT WILL PROVIDE BULK GATE API'S TO FIND MUTUAL CONNECTIONS. SO INSTEAD OF CALLING GRAPH SERVICE AND USER SERVICE FOR EACH AND EVERY USER, IT WILL FETCH ALL FRIENDS/FOLLOWERS IN A SINGLE GO REDUCING LATENCY AND SAVING TIME. IT ALSO SITS ON TOP OF SQL DB BECAUSE HERE ALSO MILLIONS OF DATA WILL BE VERY WELL STRUCTURED. 
HERE THE SQL DB WILL BE MANAGING MORE DATA AS COMPARED TO USER SERVICE SQL DB FOLLOWERS AND FOLLOWING AS WELL. WE CAN THINK OF SHARDING THE DB WHEN IT COMES TO SCALING. WE ALSO CONSIDER REDIS FOR THIS DATA OF FOLLOWERS AND FOLLOWING BECAUSE ITS VERY FREQUENTLY ACCESSED. WE WILL BE DOING THIS WITH KEY AS USER_ID AND VALUE AS OBJECT OF FOLLOWING AND FOLLOWERS.
IT WILL ALSO PROVIDE TWEET API'S AND GET API'S. 


Q. HOW USER WILL HANDLE UPLOAD OF TWEET OR PICTURE?

USER WILL GO OT UPLOAD UI FIRST IN WHICH HE WILL ADD A PICTURE AND SOME DESCRIPTION AND WILL HIT ON TWEET BUTTON. THIS WILL INVOKE THE TWEET INGESTION SERVICE. IT WILL IDENTIFY THE TWEET TYPE(WHETHER IT CONTAINS IMAGE OR VIDEO OR LONG_URL) AND THEN ACCORDINGLY IT SENDS DATA TO DIFFERENT SERVICES. LIKE IF THE TWEET CONTAINS IMAGE/VIDEO THEN IT SENDS DATA TO ASSET SERVICE (THIS ASSET SERVICE IS NOTHING BASED ON BUT NETFLIX SYSTEM DESIGN). BUT IF THE TWEET CONTAINS LONG_URL THEN IT WILL FORWARD IT TO TINY_URL SERVICE. NOW, TINY_URL SERVICE WILL GENERATE A SHORT UNIQUE URL FOR THAT PARTICULAR LONG_URL AND ADD AN ENTRY TO THE DATABASE. THEN IT WILL PROVIDE THE SHORT_URL TO TWEET INGESTION SERVICE / USER. NOW THE UPLOADED MEDIA IS MANAGED BUT THE DESCRIPTION PLAIN TEXT WOULD ALL BE STORED IN NOSQL(CASSANDRA) DB BY THE TWEET INGESTION SERVICE. 
ALSO THE TWEET INGESTION SERVICE WILL GENERATE A UNIQUE TWEET_ID FOR A TWEET AND SEND IT TO KAFKA QUEUE. 

# TWEET INGESTION SERVICE: 
IT IS RESPONSIBLE FOR SAVING THE TWEET TO DIFFERENT DATA STORES. BUT DOES NOT PROVIDE ANY SUCH API'S SO FETCH THE TWEETS.



# TWEET SERVICE:
IT IS RESPONSIBLE FOR FETCHING THE TWEETS AND PROVIDES US GET API'S. IT IS SITTING ON TOP OF CASSANDRA DB. IT IS ALSO RESPONSIBLE FOR GENERATING TIMELINE OF USERS.

Q. NOW WHEN SOME USER WILL COME TO HOME(USER'S HOME PAGE) OR USER TIMELINE(PROFILE PAGE OF SOME OTHER USER - TWEETS,USERNAME,BIO), WHAT ARE THINGS THEY WILL SEE?

SUPPOSE IF USER1 WILL VISIT THE TIMELINE OF USER2. HE WILL SEE ALL THE TWEETS MADE BY USER2, USER_NAME OF USER2 AS WELL AS THEIR BIO, ETC. USER1 WILL INVOKE TIMELINE SERVICE TO ASK THE DETAILS OF TWEETS, USERNAME, BIO TO TWEET SERVICE. NOW TWEET SERVICE WILL SEND USER2_ID TO CASSANDRA DB, AND FETCH ALL TWEETS MADE BY USER2. AGAIN, TIMELINE SERVICE WILL MANAGE AND ARRANGE THEM AND SEND THIS DATA TO USER TIMELINE. 

QUERY TO FETCH SOME USER'S TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = USER2

QUERY TO FETCH MY OWN TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = OWN_USER_ID

QUERY TO FETCH HOME TIMELINE:
SELECT* ON CASANDRA
WHERE USER_ID = <LIST_OF_FOLLOWING>


NOW IF USER GO TO HOME PAGE, WE WILL SEE THE TWEETS OF USERS THAT WE FOLLOW. IN THIS CASE, WE CAN FOLLOW BRUTE FORCE APPROACH. FROM HOME TIMELINE UI PAGE, REQUEST GOES TO TIMELINE SERVICE. IN ORDER TO GENERATE HOME TIMELINE, TIMELINE SERVICE MUST FIND OT ALL USERS THAT USER1 FOLLOWS. IT WILL THEN CALL GRAPH SERVICE AND THROUGH IT WILL BE FETCHING ALL DETAILS OF USERS THAT USER1 FOLLOWS. IT WILL FETCH USER_ID'S OF ALL THOSE USERS WHO USER1 FOLLOWS AND WILL SEND IT TO TWEET SERVICE. NOW TWEET SERVICE WILL FETCH ALL DIFFERENT TWEETS MADE BY USERS THAT USER1 FOLLOWS FROM CASSANDRA DB. THIS DATA IS THEN SENT TO TIMELINE SERVICE WHICH ARRANGES AND SORT THESE DATA ON BASIS OF LATEST TWEET AND SEND THIS TO HOME TIMELINE. 

BUT THE PROBLEM IN BRUTE FORCE ARISES WHEN A USER FOLLOWS 1000 PEOPLE. IN THAT CASE WE WILL BE QUERYING CASSANDRA DB AGAIN AND AGAIN FOR THIS MUCH AMOUNT OF USER THAT TOO SUPPOSE 6-7 TIMES A DAY WILL SLOW DOWN THINGS AND INCREASE LATENCY. 
SO INSTEAD OF THIS BRUTE FORCE TECHNIQUE, WE WILL CACHE THE HOME TIMELINE OF ACTIVE USERS. SINCE WE KNOW INSTAGRAM IS READ HEAVY SYSTEM, IT BECOMES GOOD APPROACH TO CACHE SOME INFORMATION.



# TWEET PROCESSOR SERVICE:
WE ALREADY KNOW THAT TWEET INGESTION SERVICE WILL SEND AN EVENT TO KAFKA( KEY(USER1)-> VALUE(TWEET1)). NOW, WE WILL BE HAVING TWEET PROCESSOR SERVICE WHICH WILL GRAB AN EVENT THAT USER1 HAS MADE A NEW TWEET1 AND WILL FIND OUT ALL FOLLOWERS OF USER1(BY TALKING TO GRAPH SERVICE) AND CREATE A TIMELINE FOR THEM SUPPOSE USERS USER4, USER5, USER6 HAVING TWEET OF USER1. WE WILL BE CACHING THIS INFORMATION IN REDIS WHERE KEY IS USER_ID AND VALUE WILL BE TWEET_ID. NOW, IF USER4 COMES AND VIEWS HOME TIMELINE UI THEN IT WILL INVOKE THE TIMELINE SERVICE WHICH WILL FIRST CHECK IN REDIS DO WE HAVE AN ENTRY IN REDIS. REDIS WILL PROVIDE RESPONSE BY GIVING DATA TO TIMELINE SERVICE WHICH WILL RETURN DATA TO BE DISPLAYED IN TIMELINE UI. 

* BRUTE FORCE APPROACH FLOW:- USER4 -> TIMELINE SERVICE -> GRAPH SERVICE -> FIND ALL FOLLOWING -> TWEET SERVICE -> CASSANDRA -> FETCH THOUSANDS OF TWEETS -> SORT(TIMELINE SERVICE) -> RETURN

* TWEET PROCESSOR SERVICE IMPROVISED FLOW:- USER4 -> TIMELINE SERVICE -> REDIS -> PRE-COMPILED HOME TIMELINE -> USER4

WE CAN NOTICE HOW OUR FLOW DECREASED. WE CALL THIS TECHNIQUE AS FAN-OUT-ON WRITE. 


NOTE:- WE WILL NOT STORE THE HOME TIMELINE OF ALL THE USERS INSTEAD WE STORE FOR THE USERS WHO ARE ACTIVE(ACCESSED INSTAGRAM IN LAST 3 DAYS). 


Q. HOW WILL SYSTEM FIND OUT WHETHER USER IS A ACTIVE OR PASSIVE USER?
ANS - TIMELINE SERVICE WILL ASK THE USER PROFILE SERVICE TO GET THE INFORMATION ABOUT LAST LOGIN. IF ACTIVE THEN, INFO WILL BE FETCHED/QUERIED FROM REDIS CACHE. 

SUPPOSE IF USER4 IS PASSIVE USER(NOT ACCESSED INSTAGRAM IN LAST 3 DAYS), THEN WE ARE NOT GOING TO FIND HOME TIMELINE IN REDIS. 
RATHER IT WIL FOLLOW THE BRUTE FORCE KIND OF APPROACH IN WHICH THE USER4 COMES TO THE HOME TIMELINE AND HIS REQUEST WILL GO TO TIMELINE SERVICE WHICH WILL FURTHER PASS THIS REQUEST TO GRAPH SERVICE FINDING WHO USER4 FOLLOWS. THE GRAPH SERVICE WILL SEND THE USER_ID OF USERS WHOM USER4 FOLLOWS TO TIMELINE SERVICE. NOW, TIMELINE SERVICE WILL QUERY TWEET SERVICE ASKING TO PROVIDE ALL TWEETS MADE BY USERS WHOM USER4 FOLLOWS. TWEET SERVICE WILL QUERY CASSANDRA DB AND FIND OUT TWEETS MADE BY THOSE USERS AND PASSES IT TO TWEET SERVICE WHICH FURTHER PASSES IT DOWN TO TIMELINE SERVICE WHICH THEN ARRANGE AND SORT DATA BASED ON LATEST TWEET AND FORWARDS IT TO HOME TIMELINE PAGE. ALSO TIMELINE SERVICE ALSO SENDS THIS DATA TO REDIS AS USER4 HAS BECOME ACTIVE USER NOW. 



Q. HOW DO WE MANAGE FOR CELEBRITIES?
SUPPOSE IF USER6(CELEBRITY) HAVING 75 MILLION+ FOLLOWERS UPLOADS A TWEET THEN ARE WE GOING TO UPDATE IT TO HOME TIMELINE OF 75M+ USERS FOR A SINGLE TWEET. OF COURSE, NO. 

LETS SAY USER4 IS AN ACTIVE USER AND HE FOLLOWS BOTH USER1 AND USER2. USER2 IS NORMAL USER WILL 60 FOLLOWERS SO HIS NEW TWEET WILL BE FETCHED AND SHOWN IN HOMEPAGE OF USER4 USING THE REDIS CACHE METHOD. BUT IN CASE OF USER1 HAVING 75M+ FOLLOWERS, FROM THE HOME PAGE, TIMELINE SERVICE IS INVOKED WHICH INVOKES THE GRAPH SERVICE TO FETCH ALL CELEBRITIES THAT USER4 FOLLOWS AND REQUESTS THE TWEET SERVICE TO RETRIEVE NEW TWEET INFO FROM CELEBRITY THROUGH CASSANDRA DB. WHEN CASSANDRA DB RETURN THE DATA(TWEET_ID) TO TWEET SERVICE, IT SERVES THE DATA TO TIMELINE SERVICE. TIMELINE SERVICE HAVING ACCESS OF TWEET FROM USER2 THROUGH REDIS AND TWEET FROM USER1(CELEBRITY) IN THIS WAY AND COMBINES THEM TO RETURN THIS OUTPUT TO USER4.

# TRENDS WORKING:-
WHEN SOMEONE UPLOADED A NEW TWEET WITH A HASHTAG WHICH WILL COMES TO TWEET INGESTION SERVICE WHICH WILL SEND AN EVENT TO KAFKA. NOW KAFKA SENDS THIS EVENT TO FILTER OPERATOR.
LET'S SAY DONALD TRUMP UPLOADED A TWEET WITH #ELECTION #WIN HASHTAGS. USER1, USER2 AND USER3 ALSO UPLOADED A TWEET WITH #FUN #FOOD.

FILTER OPERATOR IDENTIFIES THAT #FUN AND #FOOD IS VERY COMMON HASHTAGS SO IT DISCARDS THEM AS EVERYONE USES THEM DAILY AND REMOVES THEM FROM PIPELINE. IF THE TWEET DOES NOT CONTAIN ANY COMMON HASHTAGS AND KEYWORDS THEN IT SENDS TWEET TO THE PARSE OPERATOR. LET'S SAY DONALD TRUMP UPLOADED A TWEET WITH #ELECTION #WIN HASHTAGS, THEN IT WILL EXTRACT THE HASHTAG OR IF THE TWEET DOES NOT CONTAIN ANY HASHTAG PARSE OPERATOR WILL CREATE KEYWORDS USING SOME UNIQUE KEYWORDS MENTIONED IN TWEET. AFTER DOING THESE, PARSE OPERATOR WILL SEND THESE TO TWO DIFFERENT PIPELINES: GEO-LOCATION AND COUNT-TAG'S.

* IN COUNT-TAG'S PIPELINE, COUNT-TAG'S WILL COUNT ALL COMMON HASHTAGS LIKE #ELECTION #WIN AND MORE SIMILAR HASHTAGS AND IT WILL SEND THESE OPERATORS TO RANK OPERATOR. NOW THIS RANK OPERATOR WILL DECIDE WHICH OPERATOR HASHTAG WILL IS GOING TO BE TREND. IT WILL PROVIDE RANKS TO DIFFERENT HASHTAGS BY CREATING GROUPS OF SIMILAR HASHTAGS AND THEN RANK THESE GROUPS. 

* THERE MIGHT BE A CASE RELATED TO SOME HASHTAGS ARE ONLY SPECIFIC TO A PARTICULAR LOCATION. SUPPOSE AN ELECTION WOULD BE HAPPENING IN INDIA. OTHER GEOGRAPHIES MIGHT NOT BE GEOGRAPHY IN THAT. HENCE, ALL SUCH HASHTAGS LIKE #ELECTION #WIN ARE SPECIFIC TO INDIA ONLY. SO WE WILL BE CALCULATING WHAT ALL HASHTAGS OR KEYWORDS ARE TRENDING IN THE LOCATION. THEN SIMILARLY WE WILL COUNT ALL COMMON HASHTAGS LIKE #ELECTION #WIN AND MORE SIMILAR HASHTAGS AND IT WILL SEND THESE OPERATORS TO RANK OPERATOR. NOW THIS RANK OPERATOR WILL DECIDE WHICH OPERATOR HASHTAG WILL IS GOING TO BE TREND. IT WILL PROVIDE RANKS TO DIFFERENT HASHTAGS BY CREATING GROUPS OF SIMILAR HASHTAGS AND THEN RANK THESE GROUPS.

FINALLY, WE WILL BE STORING EVERYTHING IS REDIS FOR FREQUENT ACCESSED DATA FOR A PARTICULAR WINDOW(5/15 MINS). TWITTER WILL IDENTIFY WHAT ALL KEYWORDS AND HASHTAGS ARE TRENDING IN A PARTICULAR WINDOW. SUPPOSE A PARTICULAR HASHTAG OR GROUP OS SIMILAR HASHTAGS ARE CONTINUOUSLY TRENDING FOR 3-4 HOURS, THEN TWITTER WILL PROCESS THEM USING DIFFERENT OPERATORS AND FINALLY RANK THEM AND PUT THEM INTO REDIS.
