# CHAT SERVICE:
THERE WILL BE SEPARATE API GATEWAY/LOADBALANCER FOR THIS SERVICE OTHER THAN THE FIRST LOAD BALANCER/API GATEWAY USED FOR HANDLING HTTP REQUESTS, WHICH WILL ONLY SUPPORT WEB SOCKET CONNECTION MANAGE AUTHENTICATION, AUTHORIZATION, RATE LIMITING AND PROPER ROUTING.

ONE WAY THAT TWO USER CAN COMMUNICATE OVER INTERNET IS BY KNOWING THE IP ADDRESS OF EACH OTHER. BUT HERE INTERNET HAS BILLIONS OF USERS, AND IT IS NOT POSSIBLE THAT EACH AND EVERY USER MUST BE KNOWING IP ADDRESS OF ALL OTHER USERS. WHICH MEANS THERE ISN'T A WAY THROUGH WHICH THEY CAN DIRECTLY COMMUNICATE WITH EACH OTHER. THEREFORE, THEY CAN COMMUNICATE IN PRESENCE OF A SERVER. LET'S SAY THERE EXISTS A MESSAGING SERVER BETWEEN USER A AND USER B, THEN THE MESSAGE WILL BE SENT BY USER A TO MESSAGING SERVER THEN IT WILL BE FORWARDING THE MESSAGE TO USER B. 

Q. HOW THIS MESSAGING SERVER WILL SEND M1 MESSAGE TO USER B RECEIVED FROM USER A?
ANS - USER A WILL MAKE AN HTTP REQUEST WITH THE SERVER AND SEND M1 MESSAGE. BUT SERVER DOESN'T RANDOMLY SENDS MESSAGE TO THE CLIENT. THEREFORE, USER B HAS TO ASK TO SERVER AT EACH TIME INTERVAL WHETHER IT HAS ANYTHING TO DELIVER TO USER B OR NOT. PROBLEM ARISES IF SERVER DOES NOT HAVE ANY MESSAGE TO DELIVER TO USER B THEN ALSO USER B IS CONSTANTLY ASKING FOR A CHECK THAT SERVER IS HAVING MESSAGE TO DELIVER OR NOT IN RESPONSE OF WHICH SERVER SENDS EMPTY RESPONSES AGAIN AND AGAIN(POLLING).



# SOLUTION: WEB SOCKET SERVER 
IN WEB SOCKET CONNECTION BETWEEN CLIENT AND SERVER IS CONSISTENT AND PERSISTENT MEANING IT WILL NOT CLOSE UNTIL WE CLOSE IT. BOTH CAN SEND MESSAGES INDEPENDENTLY. BUT THE CLIENT AND SERVER DIRECTLY CANNOT MAKE WEB SOCKET CONNECTION. THE CLIENT INITIATES HTTP CONNECTION AND THEN THE SERVER DOES HANDSHAKE PERFORMING HTTP UPGRADE AFTER WHICH BIDIRECTIONAL COMMUNICATION FOR EXCHANGE OS MESSAGES IS ESTABLISHED. 

FLOW:
USER A WANTS TO CONNECT TO USER B. THE MOMENT USER A WILL CONNECT TO WIFI OR SWITCHES ON MOBILE DATA, A WEB SOCKET CONNECTION WILL BE ESTABLISHED BETWEEN THE USER A AND MESSAGING SERVER AND THE USER A SENDS MESSAGE M1 TO THE MESSAGING SERVER. NOW, MESSAGING SERVER CHECKS WHETHER USER B IS CONNECTED TO THE INTERNET OR NOT. THE MOMENT USER B GET CONNECTED TO INTERNET, A WEB SOCKET CONNECTION GETS ESTABLISHED WITH MESSAGING SERVER AND USER B AND MESSAGING SERVER DELIVERS THE MESSAGE M1 TO USER B. BUT BEFORE SENDING, IT WILL STORE THE M1 MESSAGE IN DATABASE ALONG WITH SENDER_ID, RECEIVER_ID. HERE THE DB USED WOULD BE NOSQL DATABASE(CASSANDRA). SUPPOSE IF USER IS NOT CONNECTED TO INTERNET, AND TRIES TO SEND MESSAGE M2, MESSAGE NOW CANNOT BE STORED INTO CASSANDRA DB BECAUSE OF LACK OF INTERNET CONNECTIVITY. SO IN THIS CASE MESSAGE M2 WILL BE STORED IN DEVICE'S LOCAL DATABASE(SQL-LITE3). NOW THE MOMENT USER A WILL GET CONNECTED TO INTERNET, A WEB SOCKET CONNECTION WILL BE ESTABLISHED BETWEEN THE USER A AND MESSAGING SERVER AND THEN USER A WILL READ MESSAGE FROM LOCAL DB AND SEND THIS MESSAGE M2 TO MESSAGING SERVER WHICH WILL THEN CHECK WHETHER USER B IS CONNECTED TO INTERNET OR NOT. IF NOT, IT WILL STORE MESSAGE M2 IN CASSANDRA DB ALONG WITH SENDER_ID, RECEIVER_ID. AS SOON AS USER B CONNECTS TO INTERNET, A WEB SOCKET CONNECTION WILL BE ESTABLISHED BETWEEN THE USER B AND MESSAGING SERVER AND MESSAGING SERVER WILL READ MESSAGE M2 FROM DATABASE AND SENDS MESSAGE M2 TO USER B. 

AS WE KNOW 100B MESSAGE TRANSFER EVERYDAY,  WE HAVE TO HORIZONTALLY SCALE OUR MESSAGING SERVER. NOW THESE USERS WILL TRY TO CONNECT MESSAGING SERVER BUT THEY CANNOT DO IT RANDOMLY, AS LOAD BALANCERS COMES IN ACTION. HERE LOAD BALANCERS DECIDE WHICH SERVER TO CONNECT WITH AND PREVIOUS SESSION OF CLIENT WITH SERVER. SUPPOSE IF LOAD BALANCER WILL MAKE CLIENT CONNECTION OF USER A WITH MESSAGING SERVER 1 TO SEND MESSAGE M1, BUT WHAT IF MESSAGING SERVER 1 GOT CRASHED. IN THIS CASE HOW WILL CLIENT/USER A SEND THE MESSAGE TO USER B OR HOW WILL IT GET MESSAGES FROM OTHER USERS? WE CAN'T TELL THE SERVER THAT SERVER 1 GOT CRASHED AND WE CANNOT SEND THE MESSAGE.
SO TO AVOID THIS, WE WILL USE KAFKA QUEUE BEFORE SENDING MESSAGE TO MESSAGING SERVE 1. NOW LOAD BALANCER WILL NOTICE, MESSAGE SERVER 1 GOT CRASHED AND THE KAFKA QUEUE IS CONTAINING M1 MESSAGE SENT BY USER A AND TO BE DELIVERED TO USER B. SUPPOSE USER B ESTABLISHES CONNECTION WITH MESSAGING SERVER 2. IN THIS CASE, LOAD BALANCER WILL TELL MESSAGING SERVER 2 THAT THERE IS A MESSAGE FOR USER B IN KAFKA QUEUE. THIS MESSAGING SERVER 2 WILL GO TO KAFKA, READ THE MESSAGE AND SEND IT TO USER B. NOW SINCE LOAD BALANCER KNOW MESSAGING SERVE 1 GOT CRASHED SO IT WILL ESTABLISH CONNECTION OF USER A WITH SOME OTHER MESSAGING SERVER. HENCE BYB THIS WE CAN SHARE MESSAGES EVEN IF A SERVER GOT FAILED. 




# FUNCTIONING OF MESSAGING SERVER:
AS SOON AS USER A CONNECTS TO INTERNET, A WEB SOCKET CONNECTION ESTABLISHES WITH USER A AND MESSAGING SERVER 1 AND A PROCESS WILL BE CREATED FOR THAT PARTICULAR CONNECTION. THIS PROCESS WILL BE HAVING P_ID, AND A QUEUE ASSOCIATED TO THE PROCESS. IN THIS QUEUE WE WILL STORE ALL THE MESSAGE THAT ARE SENT BY OTHERS TO USER A. 
SIMILARLY, WHEN USER B CONNECTS TO INTERNET, A WEB SOCKET CONNECTION ESTABLISHES WITH USER B AND MESSAGING SERVER 2 AND A PROCESS WILL BE CREATED FOR THAT PARTICULAR CONNECTION. THIS PROCESS WILL BE HAVING P_ID, AND A QUEUE ASSOCIATED TO THE PROCESS. IN THIS QUEUE WE WILL STORE ALL THE MESSAGE THAT ARE SENT BY OTHERS TO USER B. REMEMBER THE MOMENT CONNECTION GETS CLOSED THESE PROCESS WILL BE KILLED AND CONNECTION GETS CLOSED. FOR EVERY NEW CONNECTION, P_ID WILL BE DIFFERENT BUT WE NEED P_ID TO BE MAPPED WITH USER SO WE WILL STORE THIS MAPPING IN REDIS CLUSTER AS WE CANT IN DATABASE SINCE P_ID GETS CHANGED EVERY TIME. NOW WHEN USER A SENDS MESSAGE M1 TO MESSAGING SERVER 1 THEN PROCESS WITH P_ID 1 WILL GRAB THE MESSAGE M1 AND WILL FIND THE CONNECTION THROUGH P_ID OF USER B. SO NOW PROCESS P1 WILL IDENTIFY CONNECTION TO USER B IS MANAGED/HANDLED BY PROCESS WITH P_ID 2. NOW SENT THE M1 MESSAGE INTERNALLY INTO THE QUEUE OF THE PROCESS WITH P_ID 2.
IF CONNECTION BETWEEN USER B AND MESSAGING SERVER 2 GETS CLOSED THEN THE ENTRY OF P_ID - 2, U_ID - B GETS REMOVED AND IF USER B IF CONNECTS AGAIN WITH MESSAGING SERVER 3 THEN ENTRY IS MARKED AGAIN AS P_ID - 3, U_ID - B IN REDIS. 



THERE IS ONE MORE METHOD OF CONNECTION LIKE WHENEVER USER1 IS CONNECTED OR GOING TO CONNECT TO CHAT SERVER WE WILL CALL IT AS WEB-CONNECTION1(A CONNECTION OBJECT TO START ANY CONNECTION IN WHATSAPP) AND FOR USER2 SUPPOSE WEBSOCKET-CONNECTION 2. UNTIL USERS ARE ACTIVE THEIR WEB-CONNECTION SHOULD NOT DIE. WE KNOW THAT CHAT WILL HAVE SEND OBJECT HAVING MESSAGE M1, USER1 , USER2 AND FOR USER1 TO COMMUNICATE TO USER2, FIRST WHEN USER1 ESTABLISHES CONNECTION TO WEBSOCKET-CONNECTION AND CHAT SERVICE RECEIVED A MESSAGE M1 FROM USER1. THE CHAT SERVICE WILL TRY TO SEARCH THE CONNECTION IN WHICH WEBSOCKET-CONNECTION USER2 IS CONNECTED AND FOR THAT WE HAVE TO MAKE A REQUEST INTO THE MAPPING OBJECT AND LOCATE WHERE THAT WEBSOCKET-CONNECTION IS LOCATED. WHEN FOUND USER2 IS CONNECTED TO WEBSOCKET-CONNECTION 2, THEN CHAT SERVICE WILL SIMPLY SEND THE MESSAGE M1 TO USER2 USING WEB-SOCKET CONNECTION THAT IS ALREADY OPENED. ALL OF THIS INFO OF MAPPING OBJECT(USING WHICH WEBSOCKET-CONNECTION OF PARTICULAR USER IS FOUND) IS STORED IN REDIS CACHE(A WEBSOCKET REGISTRY TO PERSIST THE INFO ABOUT WHICH USER IS CONNECTED TO WHICH WEBSOCKET-CONNECTION). SINCE THE AMOUNT OF USERS ARE TOO MANY,  IT IS NOT POSSIBLE OT OPEN WEBSOCKET-CONNECTION FOR EACH USER SO ALONG WITH EVERY WEBSOCKET-CONNECTION WE WILL BE HAVING TTL(TIME-TO-LIVE), IF USER IS NOT ACTIVE WEB SOCKET CONNECTION WILL GET DELETED FROM WEB-SOCKET REGISTRY. SUPPOSE USER1 GOT DISCONNECTED TO WHATSAPP AND COMES AFTER SOME TIME AND WHEN IT SENDS REQ TO WEBSOCKET GATEWAY WHICH WILL SEE THERE IS NO PREDEFINED CONNECTION PRESENT AND SO IT ESTABLISHES A NEW WEBSOCKET-CONNECTION FOR USER1 AGAIN. 
IS USER1 IS SENDING MESSAGE M1 TO USER3 AND HE IS OFFLINE THEN THIS MESSAGE TROUGH CHAT SERVICE WILL BE PERSISTED IN CHAT DB. 

LET'S CONSIDER USER A GOT CONNECTED WITH MESSAGING SERVER 1 AND USER B GOT CONNECTED TO MESSAGING SERVER 2. NOW USER A WANTS TO SEND M1 MESSAGE TO USER B SO FIRST LOAD BALANCER WOULD COME INTO ACTION ALLOCATING MESSAGING SERVER 1 TO USER A. NOW MESSAGING SERVER 1 HAS M1 MESSAGE, THE FIRST APPROACH WOULD BE USING KAFKA QUEUE IN WHICH THE MESSAGE WOULD BE FIRST STORED IN KAFKA QUEUE AND THEN USER B READS FROM THE KAFKA QUEUE EVEN WHEN CONNECTED TO MESSAGING SERVER 2. 
ANOTHER APPROACH WOULD BE USING RPC CALLS. IN THIS CASE, MESSAGING SERVER 1 WOULD GET TO KNOW THAT IT DOESN'T HAVE CONNECTION WITH MESSAGING SERVER 2 SO IT WOULD INTERNALLY FORWARD THIS REQUEST(USING RPC) TO MESSAGING SERVER 2 AND THEN MESSAGING SERVER 2 WOULD SEND THIS MESSAGE M1 TO USER B. HERE, WE CAN ALSO CONSIDER REDIS STREAM RATHER THAN KAFKA WHICH PROVIDE LESS LATENCY THAN KAFKA STREAM. SUPPOSE USER A SENDS MESSAGE TO MESSAGING SERVER 1 AND IT FINDS USER B IS OFFLINE THEN IT WILL STORE MESSAGE M1 IN REDIS STREAM IN THE CHANNEL TO WHICH MESSAGING SERVER 1 IS SUBSCRIBED TO(LIKE CHANNEL1) AND ALSO NOTIFICATION SERVICE COMES HERE IN ACTION TO NOTIFY THE USER B ABOUT A MESSAGE BEING RECEIVED WITH THE HELP OF FIREBASE CLOUD MESSAGING. 


# MESSAGE ACKNOWLEDGEMENT:
AS SOON AS CONNECTION BETWEEN USER A AND MESSAGING SERVER 1 GETS ESTABLISHED VIA WEB SOCKET AND MESSAGING SERVER SUCCESSFULLY RECEIVES MESSAGE M1 SENT BY USER A, THEN THE SERVER SENDS AN ACKNOWLEDGEMENT/RESPONSE SIGNIFYING THAT MESSAGE HAS BEEN RECEIVED BY IT AND THEREFORE SINGLE TICK APPEARS. DOUBLE TICK MARK APPEARS WHEN THE MESSAGING SERVER DELIVERS MESSAGE M1 TO USER B SUCCESSFULLY WHEN IT IS ACKNOWLEDGED BY USER B. THE MOMENT USER B WILL OPEN WHATSAPP AND READ THE CHAT, IT WILL AGAIN SENDS AN ACKNOWLEDGEMENT TELLING IT HAS READ THE MESSAGE M1 THAT TO THE MESSAGING SERVER 1. THEN THE MESSAGING SERVER 1 SENDS AN ACKNOWLEDGEMENT TO USER A TELLING MESSAGE M1 HAS BEEN READ BY USER B. THE MOMENT THIS ACKNOWLEDGEMENT IS RECEIVED BY USER A BLUE TICK APPEARS. 

* LAST SEEN:-
OUR DEVICES ARE CONFIGURED IN SUCH A WAY THAT WHEN IT IS CONNECTED TO THE INTERNET IT WILL SEND HEARTBEAT AT EACH TIME INTERVAL CONTINUOUSLY(LIKE INTERVAL OF 5 SECONDS) IF USER IS ACTIVELY USING THE APPLICATION. THE SERVER WILL STORE THIS INFORMATION AS MAPPING OF SUPPOSE U_ID AND TIMESTAMP IN REDIS. THE SERVER WILL READ THIS ENTRY AND WILL SEND THIS INFORMATION OT USER B.



# GROUP CHAT: (LIST ITS WORKING)
ONCE REQUEST OF USER A COMES TO THIS CHAT SERVICE, IN TURN CHAT SERVICE MAKES AN API CALL TO GROUP SERVICE TO VIEW THE MEMBERS PRESENT(USER_ID'S) IN THE GROUP BASED ON GROUP_ID. ONCE WE HAVE LIST OF ALL THE USER_ID'S PRESENT WITHIN THE GROUP, WE HAVE TO ACTUALLY SEND MESSAGE TO EACH AND EVERY MEMBER OF THE GROUP. IT MAY LOOK LIKE WE ARE JUST BROADCASTING THE MESSAGES BUT IT IS NOT HOW IT FUNCTIONS. WE HAVE TO ACTUALLY SEND THIS MESSAGE INDIVIDUALLY TO EACH MEMBER OF THIS GROUP BECAUSE AS WE CAN NOTICE THERE WOULD BE SOME USERS WHO HAVE RECEIVED AND READ THE MESSAGES, RECEIVED THE MESSAGES BUT NOT READ AND SOME WHO DID NOT RECEIVE THE MESSAGES. 

ALL THESE THREE CASES HAVE BEEN DISCUSSED ABOVE IN CHAT SERVICE.

GROUP DB AS WELL AS GROUP MAPPING DB(SQL DB FOR BOTH) TELL WHY WE USED SQL FOR BOTH.



# MEDIA SERVICE:
FOR SEPARATION OF CONCERNS AND LESS LOAD ON MESSAGING SERVER , WE WILL CONFIGURE AN HTTP SERVER AND PUT CDN ON TOP OF IT. LET'S SAY USER A WANTS TO SEND AN IMAGE TO USER B.  FIRST USER A SENDS THIS IMAGE TO HTTP SERVER WHICH FURTHER STORES THIS IMAGE INTO CDN. THE HTTP SERVER THEN WILL GENERATE A UNIQUE HASH-CODE FOR PARTICULAR IMAGE AND WILL SEND IT TO USER A ALONG WITH MEDIA_TYPE. USER A WILL BE HAVING UNIQUE HASH-CODE NOW AND WILL SEND THIS HASH-CODE TO MESSAGING SERVER 1 WHICH WILL ON RECEIVING THE HASH-CODE SEND THIS HASH-CODE TO USER B. NOW USER B WILL GO TO THE HTTP SERVER ALONG WITH THE HASH-CODE AND WILL ASK FOR IMAGE. THE HTTP SERVER WILL VERIFY THE HASH-CODE AND ON SUCCESSFUL VERIFICATION WILL ALLOW USER B TO DOWNLOAD THE IMAGE FROM CDN. 


# MESSAGE ENCRYPTION:
UNTIL NOW WE WERE SENDING MESSAGE M1 FROM USER A TO USER B VIA MESSAGING SERVER. BUT FOR SECURITY AND PRIVACY REASONS, WE DON'T WANT OTHERS TO READ THIS MESSAGE M1 NOT EVEN THE SERVER. SO WE REALLY NEED TO ENCRYPT THE MESSAGE. MEANING WHEN USER A WILL SEND MESSAGE M1 TO SERVER IT WILL BE ENCRYPTED AND SENT TO MESSAGING SERVER WHICH THEN PASSES MESSAGE TO USER B WHICH IS IS THEN AGAIN DECRYPTED AT USER B'S SIDE TO GET THE EXACT MESSAGE M1. 

* FOR DOING THIS WE USE PRIVATE AND PUBLIC KEY CONCEPT:
WHEN A USER RESISTERS HIMSELF ON THE SYSTEM, THE SYSTEM GENERATES PRIVATE KEY AND A PUBLIC KEY FOR EACH USER. THE PRIVATE KEY REMAINS ON USER'S DEVICE WHILE PUBLIC KEY IS SHARED WITH SERVER SO THAT OTHER USERS CAN USE IT TO DECRYPT THE MESSAGE. THE MOMENT USER A AND B REGISTER THEMSELVES IN APPLICATION THEIR PUBLIC KEYS WILL BE SHARED TO SERVER. BUT WHY?

NOW MESSAGING SERVER HAS BOTH PUBLIC KEYS OF USER A AND USER B. IF NOW USER A WANTS TO SEND MESSAGE M1 TO USER B THEN IT WOULD ASK THE MESSAGING SERVER 1 TO PROVIDE PUBLIC KEY OF USER B.  MESSAGING SERVER 1 WILL SEND USER B'S PUBLIC KEY. USING THIS PUBLIC KEY USER A WILL ENCRYPT THE MESSAGE AND THEN SEND MESSAGE(M1 + PUBLIC KEY) TO MESSAGING SERVER WHICH WILL SEND THIS ENCRYPTED MESSAGE TO USER B. NOW USER B HAS ITS PRIVATE KEY USER B CAN DECRYPT THE MESSAGE.

AT THIS TIME WE DON'T NEED ANY MESSAGE SEARCH SERVICE TO STORE MESSAGES. 




# AUDIO-VIDEO CALL SUPPORT:


Q. HOW WE WILL SHOW THAT USER IS ONLINE OR OFFLINE?
ANS - WHOEVER IS ACTIVE FOR A PARTICULAR INSTANCE OF TIME, FOR THAT USER WEB SOCKET CONNECTION SHOULD BE ALSO ACTIVE MEANS HIS ENTRY WOULD BE PRESENT IN WEB SOCKET REGISTRY(IN REDIS CACHE). AND IF ENTRY IS PRESENT IN REGISTRY WE CAN SAY USER IF ONLINE OTHERWISE SHOW OFFLINE AND SHOW THE TIME FRAME WHEN HE HAS AVAILABLE(LAST SEEN) USING THE LAST_SEEN VARIABLE IN USER_DB. SO WE HAVE TO MAKE A CONNECTION BETWEEN USER AND REDIS CACHE, USING CDC PIPELINE MANAGED BY USER MANAGEMENT SERVICE TO UPDATE THE USER STATUS WHETHER ONLINE OR OFFLINE AND LAST SEEN. 


* ONCE USER COMES WEB SOCKET CONNECTOR, THE CHAT SERVICE WILL CHECK THAT WHETHER IS ANY PENDING MESSAGES FOR USER OR NOT. FOR THIS WE WILL HAVE ONE MORE MESSAGE SERVICE WHICH WILL FETCH THE UNSENT MESSAGES FROM CHAT DB.
