# QPS FOR EACH SERVICE:
* QPS - HOW MANY TIMES WE QUERY DATABASE PER SECOND FOR INFORMATION. 
* WRITE - IF WE MAKE ANY CHANGE IN DATABASE
* READ - QUERYING THE DATABASE IN WHICH WE ARE NOT MAKING ANY CHANGES IN DATABASE.

TWO MAJOR SERVICES IN WHICH WE QUERY OUR DATABASE:
1. SEARCHING SERVICE(HOTEL/ROOM) - READ 
2. BOOKING SERVICE - WRITE



# BALLPARK FIGURES:
* WRITE OPERATIONS - THERE IS 80% OF ROOM OCCUPANCY. LET'S SAY EACH USER MADE A BOOKING FOR AT LEAST 4-5 DAYS. THEREFORE:- 2X10^6 X 0.8 / 4 FOR EACH DAY, AROUND 4(TPS - TRANSACTION PER SECOND) BOOKINGS PER SECOND.

* READ OPERATIONS - THERE IS 10 % OF FUNNEL CONVERSIONS ,i.e, ONLY 10 PEOPLE WILL BOOK A ROOM OUT OF 100 AFTER SEARCHING HOTEL(S), ROOM(S). 
TPS FOR BOOKING - 4
READ QPS - 4 -> 40 -> 400 QPS


WRITE OPERATIONS ARE VERY LOW BUT READ IS HIGH, AND WE CAN HAVE DIFFERENT ENTITIES IN OUR SYSTEM(USER, HOTEL, ROOM) AND SINCE TWO USERS CAN BE BOOKING AT THE SAME TIME SO THERE MAY BE TRANSACTION RELATED QUERIES FOR TAKING CARE OF ACID PROPERTIES SO FOR THAT WE USE SQL DATABASE IN OUR SYSTEM.


NOTE:- FOR EACH SERVICE WE WILL USE MASTER SLAVE ARCHITECTURE TO ENSURE HIGH AVAILABILITY IN CASE ANY SLAVE GOES DOWN, OTHER SLAVE WILL SERVE.

# HOTEL SERVICE:-
WHENEVER PRODUCER GENERATES AN EVENT WITH PAYLOAD(HOTEL/ROOM METADATA) FOR ADDITION/DELETION OF HOTELS/ROOMS, IT IS SENT TO THE KAFKA QUEUE WHICH SENDS THIS TO SEARCH SERVICE ACTING AS CONSUMER. SO SEARCH SERVICE LISTENS TO THE EVENTS CREATED BY THE PRODUCERS THEN SEARCH CONSUMERS SENDS THESE TOPICS TO ELASTIC SEARCH CLUSTERS. NOW WE NEED CACHE MEMORY ALSO HERE BECAUSE READ OPERATION QPS IS VERY HIGH. SO WE WILL CREATE A CDN ON TOP OF HOTEL SERVICE TO STORE STATIC DATA(LIKE IMAGES AND VIDEOS OF HOTELS, ROOMS). THROUGH THIS CDN, ELASTIC SEARCH CLUSTER WILL GET THE STATIC DATA. 


# BOOKING SERVICE:
WE WILL USE INVENTORY TABLE AND HOTEL, ROOM TABLE AND BOOKING TABLE.

SINCE WE KNOW FOR WRITE SERVICE OUR QPS WAS VERY LOW, WE CAN USE SQL CLUSTERS(EG: MYSQL). IF USER CLICKS ON RESERVED, BUT BOOKING IS NOT CONFIRMED SINCE PAYMENT IS NOT DONE. IF USER COMPLETES THE PAYMENT SO THE STATUS OF BOOKING IS CONFIRMED NOW. EVEN AFTER CLICKING ON RESERVED IF WE DON'T MAKE ANY PAYMENT THE STATUS WOULD BE CANCELLED. 

* PROCEDURE OF BOOKING:
1. SELECTION OF ROOM
2. CHECK INVENTORY(WHETHER ROOMS OF AVAILABLE OR NOT)
3. MAKE PAYMENT(IF PAYMENT IS SUCCESSFUL THEN REDUCE INVENTORY BY 1)


Q. WHAT IF I WANT TO FETCH MY PREVIOUS BOOKING DATA?
ANS - WE CAN USE THE SAME SQL CLUSTER FOR FETCHING PREVIOUS COMPLETED BOOKINGS BUT WE WILL NOT SINCE THE QPS FOR READ OPERATIONS WAS VERY HIGH INCREASING THE LOAD ON BOOKING SQL CLUSTER SO FOR THAT WE WILL USE ANOTHER SERVICE KNOWN AS BOOKING MANAGEMENT SERVICE(FOR ALL READ OPERATIONS). WE ALSO NEED SOME KIND OF STORAGE FOR STORING THESE COMPLETED BOOKINGS DUE TO WHICH WE USE REDIS CLUSTER.

SO WHENEVER USER WANTS TO FETCH SOME PREVIOUS COMPLETED BOOKINGS FIRST IT WILL BE CHECKED IN REDIS. IF FOUND THEN RETURNED AND IF NOT THEN IT WILL FETCH THAT FROM SQL DB AND ADD AN ENTRY IN REDIS AS WELL. 

WHEN OUR HOTEL WILL BE NEW THERE WOULD BE LINEAR AMOUNT OF BOOKINGS, BUT AFTER SOME TIME THERE WOULD BE EXPONENTIAL INCREASE IN NO. OF BOOKINGS. 

* INTIAL BOOKINGS= 4TPS
THERE ARE 86,400 = 10^5 SECONDS IN A DAY
SO BOOKINGS PER DAY = 4 X 10^5
AND FOR 100 DAYS = 4 X 10^5 X 10^2 = 4 X 10^7

SO IT IS NOT GOOD TO STORE THE DATA IN SAME SQL CLUSTER WITH CURRENT BOOKINGS AND PREVIOUS ALL BOOKED DATA. THE ANSWER IS NO. FOR COMPLETED BOOKINGS WE CAN USE CASSANDRA(NOSQL DB) TO STORE LARGE AMOUNTS OF COMPLETED BOOKINGS. 

ARCHIVAL SERVICE IS RESPONSIBLE FOR FETCHING AND MOVING THE DATA FROM SQL DB TO NOSQL(CASSANDRA DB) FOR PREVIOUS COMPLETED BOOKING DATA. 




# CONCURRENCY ISSUES THAT CAN HAPPEN IN OUR SYSTEM?

1. WHEN USER TRIES TO BOOK A ROOM(ID: ROOM123) AT T1 TIME, AND FOR SOME PURPOSE THE PAYMENT PAGE DID NOT OPEN. AGAIN,IN FRUSTRATION THE SAME USER WILL CREATE ANOTHER BOOKING AT TIME T2 FOR SAME ROOM(ROOM123) ID. NOW THIS IS DOUBLE BOOKING WITH SAME USER_ID, USER_NAME AND ROOM_ID, CHECK IN/OUT TIME, ETC. 

TO HANDLE THIS WE HAVE TWO WAYS:
* MAKE BUTTON DISABLE(FRONTEND) 
* USING IDEMPOTENT API - FOR THE SAME REQUEST SENT MULTIPLE TIMES WE WILL SEND SAME RESPONSE. LET'S SAY USER SENDS REQ1 TO SERVER AND SERVER SENDS RESPONSE RES1. AGAIN IF USER SENDS SAME REQ1 THEN SERVER WOULD ALSO REPLY BACK THE SAME RESPONSE RES1. AGAIN AND AGAIN THIS WILL GO ON HAPPENING. HERE WE CAN ALSO STORE RESERVATION_ID IN DB AS PRIMARY KEY.

2. WHEN TWO USERS TRIES TO BOOK SAME ROOMl THEN IN THAT CASE, WE WILL USE OPTIMISTIC LOCK OR PESSIMISTIC LOCK.
