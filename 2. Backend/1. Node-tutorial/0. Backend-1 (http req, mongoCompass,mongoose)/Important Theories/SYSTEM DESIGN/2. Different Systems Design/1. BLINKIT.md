# LOCATION SERVICE - 
PRODUCT RECOMMENDATION HAPPENS ON TWO OUTCOMES:
* LOCATION - IN INVENTORY SERVICE, ONE SERVER CANNOT MANAGE ALL THE CELLS SO EACH SERVERS HANDLES SOME CELL IN A REGION. WE USE CONSISTENT HASHING TO BALANCE LOAD ON DIFFERENT SERVERS 


* FREQUENTLY ACCESSED PRODUCTS - SHARDING TECHNIQUE(PROTEIN SHARD) TO RECOMMEND PRODUCTS TO USERS. WE CAN USE REDIS CLUSTER FOR FASTER RETRIEVAL.


# SEARCH SERVICE - 
SEARCH BASED ON TWO PARAMETERS:
* PRODUCT NAME - FUZZY SEARCHING, AUTOCOMPLETE SEARCHING, DB - ELASTIC SEARCH CLUSTER..

Q. HOW WILL ELASTIC SEARCH CLUSTER WILL KNOW THIS IS THE PRODUCT / PRODUCT CATEGORY

* PRODUCT CATEGORY(PROTEIN) - 

FLOW OF SEARCH SERVICE - 
SUPPOSE OUR USER SEARCHES PEANUT BUTTER , THEN GATEWAY WILL COME IN ACTION. THE GATEWAY THEN FORWARDS THIS REQUEST TO THE PROFILE SERVICE FOR AUTHENTICATION WHICH THEN SENDS YES/NO. THEN IT GATEWAY WILL FORWARDS REQ TO SEARCH SERVICE, WHICH THEN FURTHER PASSES REQ TO LOCATION SERVICE ALONG WITH LAT AND LONG. THEN LOCATION SERVICE PASSES REW TO GOOGLE S2 IT IT WLL RECURSIVELY DIVIDE EARTH'S MAP INTO SMALLER GRID(CELLS) AND EACH CHUNK(CELLS) REPRESENTS A REGION. NOW THIS GOOGLE S2 LIBRARY WILL SEND GRID/CELL ID TO LOCATION SERVICE POINTING USER IN THIS REGION(5). 
NOW LOCATION SERVICE RETURNS GRID ID TO SEARCH SERVICE. NOW SEARCH SERVICE HAS PRODUCT NAME LIKE PEANUT BUTTER AND GRID ID AS WELL. NOW SEARCH SERVICE WILL TO GO ELASTIC SEARCH CLUSTER AND WILL ASK FOR ALL RELATED MATCHES FOR PEANUT BUTTER. ELASTIC SEARCH CLUSTER WILL MAKE A LIST OF ALL PRODUCTS RELATED TO PEANUT BUTTER NAME OR ITS CATEGORY AND THEN RETURNS THIS LIST TO SEARCH SERVICE. NOW THIS ELASTIC SEARCH CLUSTER IS STORING THE INFORMATION(PRODUCTS, CATEGORY) BUT IT IS NOT THE SOURCE OF TRUTH LIKE IT DOES ONT HAVE IDEA OF STOCKS(AVAILABILITY). THIS IS THE REASON IT SENDS LIST OF PRODUCTS TO SEARCH SERVICE INSTEAD OF USER DIRECTLY. NOW SEARCH SERVICE WILL SEND THIS LIST TO INVENTORY SERVICE WHICH RECEIVES  THE LIST OF PRODUCTS AND GRID ID. SINCE THERE CAN ME MILLIONS ND BILLIONS OF GRID/CELLS IN MAP SO ONE SERVER WILL NOT BE ABLE TO HANDLE TRAFFIC AND CELLS SO WE CAN HAVE MULTIPLE SERVERS IN THAT CASE. SO INVENTORY SERVICE WILL CONTACT S4 SERVER MANAGING GRID/CELL 4,5. WE KNOW EACH SERVER WOULD HAVING ITS OWN DATABASE SO S4 SERVER SEARCHES THE PRODUCT(PEANUT BUTTER) AND IT WOULD ALSO HAVE THE UPDATE FOR CURRENT PRODUCT WITH STOCKS. NOW THIS SENDS THE LIST OF PRODUCTS THAT ARE AVAILABLE,IN STOCK OR WITH A MATCH TO THE INVENTORY SERVICE.  INVENTORY SERVICE SENDS THIS LIST OF PRODUCTS TO SEARCH SERVICE WHICH STORE THE INFORMATION USING REDIS CLUSTER FOR FASTER RETRIEVAL WHEN GETS A GET CALL.


Q. HOW WE ARE GOING TO STORE THE PRODUCT METADATA INFORMATION IN ELASTIC SEARCH CLUSTER?
ANS - IT WOULD BE STORING INFO IN FORMS OF MESSAGE QUEUES(KAFKA) AND ON ONE SIDE OF KAFKA QUEUE THERE WOULD BE PRODUCERS WHO WILL GENERATE TOPIC/PAYLOAD FOR EVERY NEW ENTRY REGARDING THAT ITEM/CATEGORY BY TRIGGERING AN EVERT AND SEND THESE EVENTS TO KAFKA QUEUE AND AND ON OTHER SIDE THERE WILL BE SEARCH CONSUMERS LISTENING EVENTS WHICH SEND THESE EVENTS/DATA/PAYLOAD TO ELASTIC SEARCH CLUSTERS.

Q. WHO WILL ACT AS PRODUCER HERE?
ANS - IN EACH STORE, LISTED IN BLINKIT THERE WILL BE SOME STORE MANAGEMENT SYSTEM OR DASHBOARD KIND OF PAGE AND THIS PAGE WE WIL BE ADDING NEW ENTRY OF PRODUCTS OR DELETION OF PRODUCTS FROM PAGE. LET'S SAY THESE ARE MANAGED BY SOME STORES SERVICE.THIS STORE MANAGEMENT SYSTEM WILL ACT AS PRODUCER WHENEVER A NEW PRODUCT WILL BE ADDED IN STORE THIS STORE MANAGEMENT SYSTEM WILL BE UPDATED USING STORE SERVICE OR WE CAN ADD ENTRY OF NEW PRODUCT IN THIS DASHBOARD PAGE.

Q. WHO WILL ACT AS CONSUMER HERE?
ANS - IN THIS CASE, INVENTORY SERVICE WILL ACT AS CONSUMER WHO WILL LISTEN TO THOSE TOPICS AND EVENTS FOR NEW PRODUCT.

WE CAN CREATE CDN ON TOP OF STORE SERVICE FOR STATIC DATA FOR FASTER RETRIEVAL.

TWO CASES TO CONSIDER BEFORE CHOOSING DATABASE FOR CART SERVICE: (APART FROM REDIS SINCE WE CANNOT RELY ON IT PERMANENTLY)

ACC TO SOURCES, EVERY DAY BLINKIT SERVES 2 MILLION WRITES WHICH IS HUGE. SO OUR SYSTEM WOULD BE READ AND WRITE HEAVY.

* DEVICE CHANGES(I INSTALL BLINKIT IN ANOTHER DEVICE AND LOGGED IN WITH SAME CREDENTIALS LIKE MOBILE NO, EMAIL ID AND PASS, SO IN THIS CASE MY SYSTEM SHOULD SHOW ALL PRODUCTS IN CART THAT I ADDED THROUGH OTHER PHONE)


1. PERMANENT CART FLOW:-
CART SERVICE STORES THE DATA IN NOSQL DATABASES FOR LARGE AMOUNT OF DATA HANDLING AND THEN ALSO STORES THIS DATA INTO REDIS FOR FASTER RETRIEVAL. NOW WHENEVER USER COMES TO CART AGAIN, HE WILL READ DATA FROM REDIS NOT DB. THIS IS HOW WE WILL REDUCE LOAD FROM DB. USING NOSQL DATABASE FOR DATA STORAGE WE WILL ENSURE DATA DOES NOT LOST. IF REDIS GOT CRASHED OR ITS LIMIT GOT REACHED, THEN IT WILL CHECK IN DB WHETHER IT IS PRESENT OR NOT AND RETURN THE DATA ACCORDINGLY. THEREFORE THIS IS THE NEED FOR PERMANENT STORAGE.


2. DEVICE CHANGES:- 
CART SERVICE STORES THE DATA IN NOSQL DATABASES FOR LARGE AMOUNT OF DATA HANDLING AND THEN ALSO STORES THIS DATA INTO REDIS FOR FASTER RETRIEVAL. A USER CHANGES HIS DEVICE AND LOGS IN WITH ANOTHER DEVICE USING SAME CREDENTIALS(LIKE MOBILE NO) AND WILL ASK FOR CART DATA(ITEMS STORED IN CART) IN ANOTHER DEVICE B. THEN CART SERVICE WILL AGAIN SEARCH IN DB AND RETURNS RESPONSE FOR THE REQUEST WHILE STORING THE RESPONSE IN REDIS AS WELL.



# ORDER SERVICE:

LETS SAY USER BUYS 4-5 PRODUCTS. ORDER SERVICE WILL BE RESPONSIBLE FOR PLACING AN ORDER. WE KNOW WHEN USER WANTS TO BUY ANY PRODUCT THEN CART SERVICE WILL FETCH DATA FROM DATABASE OR REDIS. CART SERVICE/ DATA STORED IN CART IS NOT THE SOURCE OF TRUTH BECAUSE IT IS NOT STORING REAL TIME DATA AS STOCKS ARE MANAGED BY THE INVENTORY SERVICE. SO BEFORE PLACING AN ORDER THE CART SERVICE SHOULD INTERACT WITH THE INVENTORY SERVICE WITH THE LIST OF PRODUCTS FOR THE UPDATE OF THE CURRENT STOCK. INVENTORY SERVICE WILL CHECK THE ITEMS IN ITS DATABASE WHETHER ITEMS ARE PRESENT OR NOT. IT RETURNS A RESPONSE BASED ON WHICH CART SERVICE DOES A VALIDATION OF THE ITEMS IN STOCK OR NOT. 

Q. IF PRODUCT  IS OUT OF STOCK CART SHOULD REMOVE THE PRODUCT BUT HOW?
ANS - USING MESSAGING QUEUE. LETS SAY THE PRODUCT GOT ADDED OR REMOVED OR OUT OF STOCK IN THE STORE WHICH IS THEN UPDATED IN STORE MANAGEMENT SYSTEM BY THE EMPLOYEES. THEN AN EVENT WILL BE OCCURRING WHICH WILL BE SENT TO KAFKA QUEUE. HERE STORE MANAGEMENT SYSTEM WILL BE ACTING AS THE PRODUCER GENERATING THE EVENT. THE MOMENT EVENT WILL BE TRIGGERED THIS WILL BE SENT TO KAFKA AFTER THAT TO CONSUMER(INVENTORY SERVICE). 

THEN AGAIN INVENTORY SERVICE WILL ACT AS PRODUCER, AND GENERATES EVENT WHICH ARE THEN SENT TO KAFKA THEREBY CONSUMED BY CART SERVICE ACTING AS CONSUMER. DUE TO WHICH CART SERVICE WILL GET TO KNOW THE PRODUCT IS OUT OF STOCK SO REMOVE IT.

IT WILL BE RESPONSIBLE FPR TRACKING THE LIVE UPDATE OF ORDERS AND STATUS OF ORDERS.


## NOW LET'S SEE HOW THEY WORK TOGETHER: (FLOW)

WE ALREADY KNOW HOW CART SERVICE IS NOT SOURCE OF TRUTH AND IT WILL INTERACT WITH THE INVENTORY SYSTEM TO CHECK WHETHER THE PRODUCTS ARE OUT OF STOCK OR NOT.
THEN THIS CART REQUEST FORWARDS THIS REQUEST TO ORDER SERVICE. NOW ORDER SERVICE AGAIN INTERACTS WITH THE INVENTORY SERVICE WHICH IS RESPONSIBLE FOR THE AVAILABILITY OF PRODUCTS(STOCKS). INVENTORY SERVICE WILL PUT A PESSIMISTIC LOCK ON THIS ASSIGNMENT OF LIKE PEANUT BUTTER MANAGING CONCURRENCY. THEN THIS INVENTORY SERVICE WILL SAY ASSIGNMENT IS LOCKED THEN IT INTERACTS WITH ORDER SERVICE TO INFORM ITEM/ITEMS HAVE BEEN SUCCESSFULLY LOCKED AND NWO ORDER CAN BE PLACED. NOW ORDER SERVICE WILL CONFIRM/ PLACE THE ORDER. THEN THE ORDER SERVICE WILL TRIGGER AN EVENT NAMED ORDER_PLACED THROUGH SOME KAFKA QUEUE. THIS EVENT WILL GO TO STORE SERVICE AND DELIVERY SERVICE THROUGH SOME KAFKA QUEUE. THE ORDER SERVICE WILL ACT AS PRODUCER AND STORE AND DELIVERY SERVICES WILL ACT AS CONSUMER LISTENING EVENTS. ORDER SERVICE WILL THEN SEND THE PRODUCT ID, STORE ID, AND PAYMENT DETAILS, ETC TO STORE SERVICE. STORE SERVICE SUPPOSE SENDS THAT REQUEST TO STORE 3, AS MENTIONED BY GIVEN STORE ID BY ORDER SERVICE. THERE WILL BE EMPLOYEES THAT WILL LISTEN TO THIS EVENT/TOPIC AND THEN AFTER GETTING TO KNOW ABOUT THE ORDER THEY WILL PACK THE ORDER AND WILL SEND THIS TO STORE SERVICE THROUGH STORE MANAGEMENT SYSTEM. STORE SERVICE WILL GENERATE AN EVENT(ORDER_PACKED) TO KAFKA QUEUE BY WHICH IT IS SENT TO DELIVERY SERVICE. HERE STORE SERVICE ACTS AS CONSUMER AND DELIVERY SERVICE AS CONSUMER. 

THIS IS HOW DELIVERY SERVICE GETS TO KNOW ORDER HAS BEEN PACKED AND DRIVER HAS TO TAKE THE ORDER FROM STORE AND DELIVER TO THE USER AT A PARTICULAR LOCATION.


NOW WE DISCUSSED HOW THINGS WILL WORK OUT WHEN ORDER SERVICE DELIVERS EVENT THROUGH KAFKA TO STORE SERVICE(CONSUMER) AS PRODUCER, LET'S DISCUSS HOW BEING PRODUCER WILL TRIGGER AN EVENT TO KAFKA WHICH THEN SENDS THIS TO DELIVERY SERVICE AS CONSUMER. 
THROUGH ORDER SERVICE, WE WILL BE SENDING USER ID, USER CONTACT, STORE ID, LOCATION TO MAKE DELIVERY BUT NOT PRODUCT DETAILS DUE TO PRIVACY(ABSTRACTION). DELIVERY SERVICE WILL LISTEN TO THOSE EVENTS AND GET TO KNOW THAT THE ITEM USER IS LOOKING FOR WILL BE CURRENTLY PRESENT AT THIS STORE. THIS DELIVERY SERVICE THEN FINDS AN APPROPRIATE PARTNER AND NOTIFY THE DRIVER VIA WEBSOCKETS THAT YOU HAVE TO TAKE AN ORDER. THEN THIS DELIVERY PARTNER WILL SEND RESPONSE THAT OK I ACCEPT AND WILL TAKE THIS ORDER. THIS DELIVERY SERVICE WILL THEN SEND THE USER ID, USER LOCATION, STORE ID, STORE LOCATION TO THE DELIVERY PARTNER. THE MOMENT DELIVERY PARTNER CONFIRMS TO DELIVER THE ORDER AN EVENT IS TRIGGERED(DELIVERY SERVICE ACTING LIKE PRODUCER) SENT TO KAFKA TO STORE SERVICE. DELIVERY SERVICE INTERACTS IN THIS WAY THAT I FOUND A DRIVER AND HE WILL BE REACHING THE STORE. 

NOW LIVE ORDER TRACKING SERVICE WILL ALSO LISTEN TO KAFKA EVENT COMING FROM STORE AND DELIVERY SERVICES. SO BOTH SERVICES WHEN GENERATES AND INTERACTS WITH EVENTS LIKE ORDER IS PACKED, DELIVERY PARTNER IS REACHING THE STORE, ORDER IS COLLECTED, DRIVER IS REACHING TO USER'S LOCATION. THIS SERVICE LISTENS THEM ALL AND WILL SEND THE CURRENT STATUS OF ORDER TO USER THROUGH WEB SOCKET CONNECTION AND SEND THEM TO USER.

# CHOICE OF DATABASE FOR EACH SERVICE:

1. PROFILE SERVICE - SQL DATABASE(POSTGRESS -> CAN STORE 100 MILLION+ ENTRIES) STORED VERY WELL IN TABLE FORMAT AS WELL AS REDIS CLUSTERS FOR HIGH SPEED DATA RETRIEVAL.

2. SEARCH SERVICE - ELASTIC SEARCH CLUSTER, AS WELL AS REDIS CLUSTERS FOR HIGH SPEED DATA RETRIEVAL.


3. CART SERVICE - NOSQL(DYNAMODB, CASSANDRA -> SINCE DATA STORED IS HUGE AS NO OF USERS ARE MANY), AS WELL AS REDIS CLUSTERS FOR HIGH SPEED DATA RETRIEVAL.


4. ORDER SERVICE - FOR LIVE ORDERS() CHOOSE SQL. THE ARCHIVER DUMP LIVE ORDERS TO SQL DB'S AND FOR STORING ORDER WE USE NOSQL DB(CASSANDRA) AS WELL AS REDIS CLUSTERS FOR HIGH SPEED DATA RETRIEVAL.

5. INVENTORY SERVICE - SQL DB(POSTGRESS) AS WELL AS REDIS CLUSTERS FOR HIGH SPEED DATA RETRIEVAL.


WE USE REDIS FOR EACH DATABASE. BUT NOT SEPARATE REDIS FOR EACH SERVICE AS WELL AS NOT SAME REDIS FOR EACH. WE ACTUALLY DIVIDE REDIS INTO DIFFERENT SHARDS AND EACH SHARDS SERVES DIFFERENT SERVICES.
