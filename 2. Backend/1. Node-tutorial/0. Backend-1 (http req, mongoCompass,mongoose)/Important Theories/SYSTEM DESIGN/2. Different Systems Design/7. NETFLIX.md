# BALLPARK FIGURES:




# FLOW:- (DISCUSS EACH SERVICE SEPARATELY)
THE CONTROL FLOW STARTS WITH THE UI FOR PRODUCTION HOUSE. THERE WILL BE A BUTTON FOR UPLOADING A VIDEO. WHEN USER CLICKS ON IT, REQUEST WILL PASS THROUGH LOAD BALANCER TO INVOKE ONBOARDING SERVICE. THIS SERVICE WILL SEND ALL DATA WITH DETAILS RELATED TO THIS VIDEO TITLE, DESCRIPTION, THUMBNAIL, TAGS, AND FINALLY THE VIDEO. ONBOARDING SERVICE TRIGGERS AN EVENT TO SEND THIS DATA TO KAFKA QUEUE BEHAVING AS PRODUCERS. MULTIPLE CONSUMERS WOULD BE LIKE NOTIFICATION SYSTEM NOTIFYING THAT XYZ PRODUCTIONS HAS UPLOADED A NEW VIDEO. 

# SEARCH SERVICE:
ANOTHER SERVICE CONSUMING KAFKA EVENT WOULD BE WOULD BE THE SEARCH SERVICE WHICH UPDATES IT TO ELASTIC SEARCH QUEUE(PROVIDES FUNCTIONALITIES LIKE FUZZY SEARCHING AND AUTO-COMPLETE) TO TELL THE USER THAT VIDEO HAS BEEN ADDED TO NETFLIX WORLD AND IT IS READY TO BE SEARCHED AND WE CAN VIEW IT OR WATCH IT. 

# CONSUMING EVENT SERVICE:
ANOTHER SERVICE CONSUMING EVENT IS CONTENT PROCESSING SERVICE WHICH WILL GRAB AND CONSUME THE RAW VIDEO FROM THE KAFKA EVENT. IT DOES ANSWER THE QUESTIONS: 

* WHERE WE WILL BE STORING THE VIDEOS
* HOW WE WILL BE STORING THE VIDEOS:-
* HOW WE WILL FETCH THE VIDEO:- 


* FLOW:-
AS WE ALL KNOW NETFLIX IS A LARGE SCALE SYSTEM,THAT MEANS WE ARE GOING TO STORE BILLIONS OF AMOUNTS OF DATA OF PRODUCTION HOUSES. SO WE CANNOT USE FILE SYSTEM TO STORE THIS AMOUNT OF HUGE AMOUNT OF DATA. HENCE, WE CAN USE AMAZON S3(BLOB STORAGE) THAT ARE STORED IN FORM OF OBJECTS BUT NOT SINGLE VIDEO AS A SINGLE OBJECT. LET'S SAY IF WE STORE IT AS A SINGLE OBJECT SO WHEN USER SKIPS(SEEKS) THE VIDEO FROM 2:30 MINS TO 4:00 MINS THEN HE WILL NOT BE ABLE TO SKIP IN THAT PART OF VIDEO SINCE IT IS STORED AS A SINGLE OBJECT[BRUTE FORCE]. IF WE USE THE RANGE REQUEST TECHNIQUE THEN ALSO THE CLIENT WILL FIGURE OUT THAT IN 4TH MIN, BYTE RANGES FROM 3000-5000 FROM IS NEED USING HTTP PROTOCOL. BUT HERE ALSO IF USER IS TRAVELING, AND NETWORK IS POOR THEN USER'S VIDEO WILL STOP AND START TO BUFFER. SO WE SOLVE THIS USING ADAPTIVE BITRATE STREAMING IN WHICH WE AUTOMATICALLY SWITCH TO DIFFERENT QUALITY VIDEOS(GOOD CONNECTION - 720P, 1080P ; POOR CONNECTION - 144P, 240P) IF NETWORK BECOMES POOR, BUT IT WILL NOT COST US BUFFERING ANYMORE. THIS IS USED FOR FETCHING VIDEO CONTENT WHERE THE QUALITY OF THE VIDEO STREAM DYNAMICALLY BASED ON USER'S NETWORK. SO THIS TECHNIQUE IS USED FOR FETCHING VIDEO AND IN ORDER TO UNDERSTAND THIS WE NEED TO UNDERSTAND HOW WE STORE VIDEO. FILE CHUNKER CAN BE USED TO DIVIDE RAW VIDEO FILE TO DIFFERENT CHUNKS(5 SECS OF VIDEO, 10 SECS OF VIDEO). 
IN ORDER TO GET DIFFERENT DEVICE FORMATS, EACH CHUNK IS DIVIDED INTO DIFFERENT FORMATS THROUGH TRANSCODER. NOW AFTER HAVING DIFFERENT TYPES OF CHUNKS AND FORMATS WE NEED DIFFERENT QUALITY OF VIDEOS. AGAIN FORMATS ARE FURTHER DIVIDED INTO DIFFERENT QUALITY VERSIONS USING QUALITY CONVERTER. THIS ALL LOOKS AS A TREE LIKE STRUCTURE. 
SO HERE WE GET TO KNOW HOW WE ARE GOING TO STORE THE VIDEO AS OBJECTS NOT THE ENTIRE VIDEO BUT ALL DIFFERENT CHUNKS, FILE FORMATS, QUALITIES. SO FOR A SINGLE VIDEO THESE ARE THE THINGS THAT WE STORE IN OBJECTS WHERE EACH OBJECT IS AROUND 5 OR 10 SECONDS OF THE VIDEO AND EACH OBJECT IS A BINARY VIDEO FILE. 


SO NOW WHEN CLIENT REQUESTS FOR CHUNKS LET'S SAY 26, 27 IS THERE HE IS NOW AND REQUESTS FOR 28,29,30 BUT SUDDENLY NETWORK BECOMES POOR THEN CLIENT AUTOMATICALLY DETERMINES THAT HE WON'T BE ABLE TO GET 28,29,30 ON TIME SO HE SWITCHES REQUEST TO LOWER QUALITY CHUNK. ACTUALLY THIS HAPPENS BECAUSE ALL CHUNKS OF LET'S SAY 144P AND 720P RUN IN PARALLEL.
* IF USER CLICKS ON PLAY VIDEO, THEN CLIENT WILL START REQUESTING FOR FURTHER CHUNKS.
* IF USER CLICKS ON PAUSE VIDEO, THEN CLIENT WILL STOP REQUESTING FOR FURTHER CHUNKS AND STORE THE RECEIVED CHUNKS TO MEMORY. 
* WHEN USER CLICKS ON SKIP BUTTON THEN ALL THE AVAILABLE CHUNKS WOULD BE FLUSHED FROM MEMORY AND FETCHES NEW CHUNKS FOR NEW VIDEO. 
* WHEN USER WANTS TO JUMPS FROM ONE CHUNK TO ANOTHER CHUNK, THEN ALL AVAILABLE CHUNKS PRESENT IN MEMORY WOULD BE FLUSHED. 



LET' COME BACK AGAIN, WHILE UPLOADING THE VIDEOS TO S3 WE WILL UPLOAD THEM TO CDN AS WELL TO REDUCE LATENCY OF OUR SYSTEM. ONE MAIN CDN CONNECTED TO DIFFERENT CDN'S CONNECTED TO DIFFERENT CDN'S ON DIFFERENT GEOGRAPHICAL REGIONS.

NOW WHEN PRODUCTION HOUSES WOULD BE UPLOADING VIDEO THEN ONBOARDING SERVICE WILL BE HANDLING THE METADATA THROUGH CASANDRA DATABASE LIKE VIDEO TITLE, DESCRIPTION, TAGS OF VIDEO, IMAGES, IMAGE URL'S. BECAUSE IN THIS CASE NETFLIX IS LARGE SYSTEM AND WE HAVE HUGE AMOUNT OF DATA BUT FINITE SET OF QUERIES. 


SEARCH SERVICE WOULD BE USING THE ELASTIC SEARCH CLUSTER(PROVIDES FUNCTIONALITIES LIKE FUZZY SEARCHING AND AUTO-COMPLETE). SEARCH SERVICE CAN TAKE CARE OF BOTH GET AND POST API REQUESTS. LIKE WHEN PRODUCTION HOUSE USER WILL UPLOAD ANY VIDEO THEN THROUGH ONBOARDING SERVICE PRODUCING EVENT AND KAFKA, THESE EVENT WOULD BE CONSUMED BY SEARCH SERVICE WHICH WILL UPLOAD THIS DATA TO ELASTIC SEARCH CLUSTER(POST API). THEN USER WHO IS GOING TO SEARCH ANYTHING WILL BE DONE WHEN SEARCH SERVICE QUERIES THE ELASTIC SEARCH CLUSTER WHICH IS WAY MORE FASTER THAN A NORMAL DB(GET REQUEST API). SEARCH SERVICE WILL ALSO TALK TO USER SERVICE AS ALL THE DETAILS OF THE USER LIKE HIS NAME, EMAIL-ADDRESS, PHONE NO ARE ALL WILL BE STORED IN SQL DATABASE ON TOP OF USE SERVICE. LET'S SAY IF A USER IS TRYING TO SEARCH A MOVIE THAT CONTAINS AGE RESTRICTION, THEN IN THIS CASE SEARCH SERVICE WILL TALK TO USE SERVICE TO GET HIS AGE DETAILS. IF USER'S AGE IS SNOT SUITABLE FOR THAT VIDEO THEN SEARCH SERVICE WILL EITHER NOT RETURN ANY RESULT OR WITH A FLAGGED TAG. REDIS CAN ALSO BE USED FOR FASTER DATA RETRIEVALS HERE. 

SEARCH SERVICE AND RECOMMENDATION SERVICE WILL BE USER FACING SERVICE WHICH WILL SERVE ON HOME PAGE ITSELF. 


# RECOMMENDATION SERVICE:
IT PROVIDES RECOMMENDATION BASED ON PREVIOUS SEARCH AND WHAT THEY WATCHED PREVIOUSLY. 

WE CAN NOTICE DATA IS BEING SENT FROM SEARCH SERVICE AND VIDEO STREAMING SERVICE TO KAFKA QUEUE. IS IS BECAUSE WHAT USER IS SEARCHING, WHAT USER IS WATCHING AND SKIPPING, FOR HOW LONG IS HE WATCHING THE VIDEO, IS HE WATCHING THE WHOLE VIDEO OR SMALL PART OF IT. AND ON THE BASIS OF THESE WE WILL PREPARE RECOMMENDATION FOR A SPECIFIC USER. THEN THE KAFKA WILL SEND THIS TO SPARK STREAM, ON TOP OF KAFKA THERE WILL BE SPARK STREAMING TO PERFORM AGGREGATION AND OTHER OPERATIONS AND HADOOP CLUSTER TO DO SOME ML OPERATIONS AND OTHER OPERATIONS TO GENERATE RECOMMENDATION FEED TO USER.

WE CAN ALSO CLASSIFY USERS TO DIFFERENT GROUPS, LET'S SAY TWO USERS WATCH SIMILAR INTEREST WATCHING FICTIONAL MOVIES. SO WE WILL PUT THEM INTO SAME CLUSTER/GROUP AND THEN WE WILL GENERATE RECOMMENDATION.

FOR THIS WE ARE USING SQL DATABASE BECAUSE EVERYTHING WHETHER USER NAME, EMAIL_ID, PHONE NO, AND HIS MORE PERSONAL DETAILS AS DATA IS VERY STRUCTURED AND CAN BE REPRESENTED USING TABLES. WE ALSO USING REDIS FOR FETCHING USER DETAILS LIKE AGE, NAME AND LOCATION FOR FASTER RETRIEVAL.
